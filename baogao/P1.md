## 一、P1 交付说明

P1 在 P0 流式聊天闭环上增加了“会话摘要 + 长期记忆 + 相关召回 + Memory UI”完整闭环。P1 不包含文件知识库、RAG、Skill 和 Tool Calling；这些能力分别留在 P2、P3。

### 1.1 完成功能

| 模块 | P1 交付能力 |
|---|---|
| 会话增量摘要 | 当未摘要消息达到阈值时，通过 LLM 合并旧摘要与新增消息；保留最近消息原文，避免上下文只剩压缩信息 |
| 长期记忆提取 | 每次助手成功回复后，从本轮用户消息和助手回答中提取用户身份、稳定偏好、长期事实或重要事件 |
| 记忆质量过滤 | 使用 `importance`（1-5）和 `confidence`（0-1）过滤低价值、低置信度候选记忆 |
| 记忆去重更新 | 使用稳定的 `normalized_key` 查找同类记忆；相同 key 更新原记录，而不是重复插入 |
| 数据库唯一约束 | 数据库强制 `(user_id, normalized_key)` 联合唯一；手动重复创建返回 HTTP 409 |
| 敏感信息过滤 | 代码级拦截凭据、私钥、JWT、身份证、银行卡、手机号、邮箱及用户明确拒绝记忆的表达 |
| 相关记忆召回 | 根据当前用户问题进行轻量文本相关性评分，召回前 N 条有效记忆并注入 Context Engine |
| 记忆生命周期 | 支持手动添加、编辑、启用、停用和删除；停用记忆保留在数据库，但不会进入模型上下文 |
| Context Engine 升级 | 上下文由 System Prompt、会话摘要、相关记忆、最近未摘要消息和当前输入共同组成，并统一受 token 预算控制 |
| Memory UI | 新增长期记忆页面，支持按类型筛选、手动添加、编辑、启停和删除，兼容桌面与移动端 |
| 数据库兼容迁移 | 应用启动时为已有 P0 SQLite 数据库幂等补齐 P1 字段，不要求用户删除原数据库 |
| 故障隔离 | 记忆提取或会话摘要失败只记录日志，不会把已经生成并持久化的正常回复改成 `run.failed` |

### 1.2 相对 P0 增加了什么

| P0 状态 | P1 改进 |
|---|---|
| 只能使用最近聊天历史 | 增加会话摘要，长对话裁剪后仍保留重要上下文 |
| `memories` 只能手动增删查 | 增加自动提取、质量过滤、去重更新、相关召回和启停状态 |
| Context 只有 System Prompt + 最近消息 | 增加摘要与相关记忆，并统一计算 token 预算 |
| 前端只有聊天视图 | 增加“对话 / 记忆”视图切换和完整 Memory 管理界面 |
| Gateway 只支持流式回答 | 增加非流式 `complete()`，供摘要和结构化记忆提取使用 |
| P0 数据表字段较少 | 扩展 `Conversation`、`Memory` 字段，并兼容迁移已有 SQLite 数据库 |
| 本轮用户消息入库后可能被历史查询再次选中 | 使用 `exclude_message_id` 排除本轮消息，避免发送给模型两次 |

### 1.3 P1 明确未做的内容

- 未引入 Embedding、向量检索或 pgvector；P1 使用 SQLite 轻量文本召回。
- 未实现文件上传、PDF/Word 解析、知识库和引用来源；这些属于 P2。
- 未实现 Skill、Tool Calling、权限审批和执行循环；这些属于 P3。
- 未实现多用户登录和鉴权；当前仍使用默认用户 `default`。

## 五、数据模型增加内容

### 5.1 Conversation 新增字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `summary` | Text，可空 | 当前会话的累计摘要 |
| `summary_message_count` | Integer | 已经进入摘要的消息数量，用于增量处理 |
| `summary_updated_at` | DateTime，可空 | 最近一次摘要更新时间 |

### 5.2 Memory 新增字段

| 字段 | 类型 | 作用 |
|---|---|---|
| `normalized_key` | String(200) | 同类事实的稳定 key，用于去重和新事实覆盖旧事实 |
| `source_conversation_id` | String(32)，可空 | 自动记忆来源会话 |
| `importance` | Integer | 重要度 1-5，低于配置阈值不保存 |
| `confidence` | Float | 置信度 0-1，低于配置阈值不保存 |
| `is_active` | Boolean | 是否允许被召回；停用不等于删除 |
| `updated_at` | DateTime | 最近一次编辑或自动更新的时间 |

### 5.3 SQLite 兼容迁移

`init_db()` 首先执行 `Base.metadata.create_all()`，然后检查现有 SQLite 表字段。缺少 P1 字段时使用固定的 `ALTER TABLE` 语句逐列补齐；重复启动时已存在的列会被跳过，因此迁移是幂等的。

创建唯一索引前会清理旧数据的 key：空 key 改为 `legacy.<id>`；重复 key 由最新记录保留，旧记录改为 `duplicate.<id>` 并停用。随后创建 `uq_memories_user_key` 联合唯一索引。该过程不删除已有记忆。

该迁移只服务当前 SQLite 阶段。进入 PostgreSQL/pgvector 后应改用 Alembic 管理正式版本迁移。

## 七、P1 完整运行逻辑

### 7.1 一次聊天的主链路

```text
用户输入消息
  ↓
POST /api/chat 校验 conversation_id
  ↓
Agent Runtime 创建 run_id
  ├─ 保存本轮用户消息
  ├─ AgentRun.status = running
  └─ 发送 run.started
  ↓
加载 Character，渲染主 System Prompt
  ↓
Context Engine 组装上下文
  ├─ 读取当前会话摘要
  ├─ 根据当前问题召回有效长期记忆
  ├─ 查询最近未摘要消息
  ├─ 排除本轮已持久化的用户消息，防止重复
  └─ 在统一 token 预算内生成 messages
  ↓
Model Gateway.stream() 调用 LLM
  ├─ openai-compatible：调用真实模型
  └─ mock：本地返回可预测流式文本
  ↓
持续发送 message.delta，前端实时渲染
  ↓
保存助手回复，AgentRun.status = completed
  ↓
发送 message.completed
  ↓
P1 后处理
  ├─ Memory Extractor 提取候选记忆
  ├─ 重要度/置信度过滤
  ├─ 按 normalized_key 新增或更新
  └─ 达到阈值时更新会话摘要
  ↓
发送 run.completed
```

主聊天生成受 `AGENT_TIMEOUT_SECONDS` 控制。记忆提取和摘要在正常回复持久化之后执行；后处理异常会写日志，但不会产生 `run.failed`。

### 7.2 Context Engine 逻辑

最终上下文优先级如下：

```text
System Prompt
  > 当前用户输入
  > 相关长期记忆
  > 会话摘要
  > 最近未摘要消息
```

具体过程：

1. 读取 Conversation 的 `summary`；
2. 从启用状态的 Memory 中召回最多 `MEMORY_RECALL_LIMIT` 条；
3. 将摘要和记忆作为明确分区追加到 System Prompt；
4. 扣除 System Prompt、摘要、记忆和当前输入的估算 token；
5. 从最新历史消息向前选择，超出预算时停止；
6. 当前输入必定保留，最近历史至少保留一条；
7. 返回 System、Messages、token 估算和召回的 memory id。

### 7.3 记忆提取逻辑

```text
本轮用户输入 + 助手回复
  ↓
prompts/memory/extract.md
  ↓
Model Gateway.complete(temperature=0)
  ↓
严格 JSON 解析
  ↓
校验 kind/content/key/importance/confidence
  ↓
阈值过滤
  ↓
按 user_id + normalized_key 查找
  ├─ 不存在：INSERT
  └─ 已存在：UPDATE 内容、来源、质量和启用状态
```

支持的记忆类型：

| kind | 含义 | 示例 |
|---|---|---|
| `profile` | 身份、习惯、稳定偏好 | 用户喜欢简洁回答 |
| `semantic` | 长期有效的事实或知识 | 用户的项目使用 FastAPI |
| `episodic` | 值得跨会话保留的重要事件 | 用户计划下周完成 P2 |

### 7.4 记忆召回逻辑

P1 不使用向量数据库。当前召回流程为：

1. 只查询当前 `user_id` 且 `is_active=true` 的最近 200 条 Memory；
2. 从当前问题和记忆内容中提取英文单词、数字、中文双字组合；
3. 按词项重合、直接包含和 importance 计算轻量分数；
4. 丢弃无相关性结果；
5. 返回得分最高的前 N 条。

该实现适合 P1 的 SQLite 和小规模个人数据。数据量增大或进入文档知识库阶段后，应在 P2 引入 Embedding 和 pgvector。

### 7.5 会话摘要逻辑

1. 计算 `消息总数 - summary_message_count`；
2. 未摘要消息少于 `SUMMARY_TRIGGER_MESSAGES` 时不调用模型；
3. 达到阈值后，将旧摘要和新增消息交给 `summary.md`；
4. 最近 `SUMMARY_KEEP_RECENT_MESSAGES` 条消息保留原文，不纳入本次摘要；
5. 保存新摘要、摘要消息进度和更新时间；
6. 下一次 Context 只查询摘要进度之后的历史消息，避免摘要和原文重复占用预算。

### 7.6 Memory UI 逻辑

- Sidebar 使用“对话 / 记忆”分段导航；新建或选择会话时自动回到聊天视图。
- MemoryView 首次挂载时读取 `/api/memories`。
- 类型页签支持全部、偏好与身份、长期事实、重要事件。
- 手动添加需要内容、类型和重要度。
- 编辑保存使用 PATCH；启用/停用只改变 `is_active`；删除才永久移除记录。
- 召回哪条记忆仍由后端决定，前端只显示和管理数据。

## 十一、当前限制与注意事项

1. **Mock 只用于联调**：Mock 的记忆提取是确定性的简单规则，不能代表真实模型质量。
2. **文本召回适合小数据量**：当前中文双字和关键词重合适合个人、小规模 Memory；大量数据需要向量召回。
3. **记忆冲突依赖稳定 key**：真实模型必须按提示为同类事实生成相同 key，否则语义相近内容仍可能重复。
4. **敏感规则需要持续维护**：当前已有代码级过滤，但新的凭据格式、国际手机号和业务专有敏感字段仍需按真实数据补充。
5. **当前默认单用户**：所有聊天和 Memory 默认属于 `user_id=default`，加入认证前不能作为多租户服务部署。
6. **SQLite 迁移是阶段方案**：进入 PostgreSQL 后应引入 Alembic，不再继续扩展手写 `ALTER TABLE`。
7. **自动提取增加模型调用**：启用 P1 后每轮聊天通常多一次提取调用，达到摘要阈值时再多一次摘要调用，需要关注费用和延迟。

## 十二、后续如何开发

### 12.1 P1 后续优化

在进入 P2 前建议先积累真实对话评估数据，而不是继续增加抽象：

1. 建立固定 Evaluation 数据集，覆盖偏好、身份、事件、否定表达、偏好变化和不应记忆内容；
2. 为记忆提取记录耗时、候选数、过滤数、插入数和更新数；
3. 增加记忆来源查看功能，让用户能回到原会话核对；
4. 在现有敏感过滤上增加可配置规则和“禁止记忆某类信息”的用户设置；
5. 根据真实数据调整 importance、confidence 和摘要阈值；
6. 处理记忆冲突，例如“以前喜欢拿铁，现在不喝咖啡”的时间和有效状态。

### 12.2 P2：理解资料

目标：让 Agent 可以读取用户上传的资料并在回答中给出来源。

建议实施顺序：

1. 设计 `File`、`DocumentChunk`、`KnowledgeBase` 数据模型；
2. 增加 `POST /api/files` 和文件状态查询 API；
3. 实现 TXT/Markdown，再逐步增加 PDF、Word 解析；
4. 实现分块、Embedding 和批量入库；
5. 数据库迁移 PostgreSQL，引入 Alembic 与 pgvector；
6. Context Engine 增加 RAG Retrieval，并与 Memory 使用独立预算；
7. SSE/回答结构增加 Citation，前端实现 Knowledge UI 和来源展示；
8. 建立检索召回率、引用正确性和无答案拒答测试集。

### 12.3 P3-P6 路线

| 阶段 | 目标 | 与 P1 的衔接 |
|---|---|---|
| P3 开始做事 | Skill、Tool Calling、Permission、Approval、Observability | Memory 为工具决策提供用户偏好；Agent Runtime 扩展为多步循环 |
| P4 连接外部 | MCP、Web Search、Browser、第三方 API | 外部结果通过统一 Tool/MCP 层进入上下文，不直接污染长期记忆 |
| P5 主动工作 | Activity、Scheduler、Queue、Worker、Background Agent | 使用用户记忆确定通知偏好和任务背景，但高风险动作仍需审批 |
| P6 高级 Agent | Planner、Replanning、自主活动、插件注册表、Evaluation | 将 Memory、RAG、Tools 作为 Planner 可选择的受控能力 |

### 12.4 P2 目录建议

仅在开始实现 P2 时新增实际需要的目录：

```text
core/
└── rag/
    ├── parser.py          # 文件解析统一入口
    ├── chunker.py         # 文本分块
    ├── embedding.py       # Embedding Gateway
    └── retriever.py       # pgvector 检索与引用结果

apps/web/components/
└── KnowledgeView.tsx      # 文件上传、处理状态、资料列表
```

不要在 P2 开始前预先创建空的 Factory、Registry 或多层 BaseClass；继续遵守“简单 > 复杂、可运行 > 完美、当前需求 > 未来需求”。

P1 已完成“认识用户”目标：Agent 能从对话中自动形成长期记忆，在后续问题中召回相关信息；长对话可以通过增量摘要继续保留重要背景；用户可以在前端查看和控制所有长期记忆。
