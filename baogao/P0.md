## 一、P0 做了什么（功能清单）

P0 交付了一个可运行的「流式聊天助手」完整闭环（后端 + 前端 + 数据库）：

| 模块 | 交付能力 |
|---|---|
| 流式聊天 | `POST /api/chat` 通过 SSE 逐字流式返回，支持停止生成、重新生成最后回复 |
| 会话管理 | 创建 / 列表 / 切换 / 重命名 / 删除会话，会话标题自动取首条消息前 20 字 |
| 消息持久化 | 用户与助手消息全部落库（SQLite），重启不丢失，多轮对话上下文正确拼接 |
| Agent Run 追踪 | 每次聊天生成 `run_id`，记录运行状态（running/completed/failed）、错误信息、Token 用量 |
| Model Gateway | 业务代码不直接绑定模型 API；`openai-compatible`（可切 DeepSeek/Qwen/智谱/Ollama）+ `mock`（无 Key 联调）双 provider |
| Context Engine | 不把全部历史塞给 LLM；System Prompt + 最近对话按 token 预算从新到旧裁剪（中英文 token 估算） |
| Character / Identity | 身份、人格、用户画像独立配置（yaml），System Prompt 模板与业务代码解耦，改人格不改代码 |
| 记忆（占位） | `memories` 表 + 手动增删查 API（自动提取在 P1） |
| 前端 UI | 会话侧栏 + 聊天区 + 输入框；流式渲染、Markdown 渲染、发送/停止/重试 |

## 四、运行逻辑

### 一次聊天的完整链路

```text
用户在浏览器输入消息
  ↓
前端 ChatView.send()：无会话则自动创建会话
  ↓
POST http://localhost:8787/api/chat  {conversation_id, message}
  ↓
FastAPI 校验会话存在（404 则拒绝）
  ↓
Agent Runtime（core/agent.py）开始一次 Agent Run（生成 run_id）
  ├─ 落库：用户消息 + run 记录（status=running）
  ├─ 发事件 run.started
  ├─ 加载 Character → 渲染 System Prompt
  ├─ Context Engine 组装上下文：
  │    System Prompt + 最近 N 条历史（token 预算裁剪，最新必保）
  │    + 本次用户消息
  ├─ Model Gateway 按配置选 provider：
  │    openai-compatible → httpx 流式调用 LLM
  │    mock             → 本地模拟流式（无 Key 联调）
  ├─ 逐字产出事件 message.delta（前端实时渲染）
  ├─ 完成后落库：助手消息 + run 更新（status=completed、token 用量）
  ├─ 发事件 message.completed / run.completed
  └─ 异常时：run 标记 failed + 发事件 run.failed
  ↓
前端收到事件流，逐字渲染；结束后从服务器重取消息列表并刷新会话标题
```

### SSE 事件协议（Agent Event Protocol 基础）

```text
event: run.started       data: {"run_id": "...", "conversation_id": "..."}
event: message.delta     data: {"content": "逐字内容"}
event: message.completed
event: run.completed     data: {"run_id": "...", "token_usage": {...}}
event: run.failed        data: {"run_id": "...", "error": "..."}
```

前端按 `event` 类型渲染不同 UI（流式文本 / 错误提示），新增事件类型不需要重写前端聊天逻辑。

### Context Engine 裁剪逻辑

1. 估算 System Prompt 的 token 数，从预算（默认 8000）中扣除；
2. 从最新消息往旧消息遍历，装得下就保留，超出预算即停止（最新消息必保）；
3. 加上本次用户输入，组成发给 LLM 的 messages。
4. Token 估算：中文 1 字 ≈ 1 token，其他字符按 4 字符 ≈ 1 token。

### 端口与配置

| 服务 | 端口 | 配置位置 |
|---|---|---|
| 后端 FastAPI | 8787 | `.env` 的 `API_PORT`、`CORS_ORIGINS` |
| 前端 Next.js | 4321 | `apps/web/package.json` 的 `-p 4321`；后端地址在 `apps/web/.env.local` 的 `NEXT_PUBLIC_API_URL` |

模型配置（`.env`）：

```env
LLM_PROVIDER=mock                    # mock | openai-compatible
LLM_BASE_URL=https://api.deepseek.com/v1   # 换模型只需改这里
LLM_API_KEY=sk-xxx
LLM_MODEL=deepseek-chat
CONTEXT_MAX_TOKENS=8000              # 上下文预算
AGENT_TIMEOUT_SECONDS=120            # 单次 Run 超时
```

按合并架构文档的 P0-P6 路线，P0 已完成，后续阶段：

| **P4 连接外部** | MCP、Web Search、Browser | 新增 `core/mcp/`；Gateway 增加 Web Search 等原生工具 |

### 下一步（P1）建议实施顺序

1. 会话摘要：每次 Run 完成后由 LLM 压缩生成摘要，存入 conversation；
2. Memory Extractor：从对话中提取「用户事实/偏好/事件」，经重要度过滤后写入 `memories`；
3. Context Engine 接入记忆召回：把相关记忆注入上下文（可先用关键词/规则检索，再上向量）；
4. 前端 Memory 管理页（查看/编辑/删除/禁止某条继续记忆）；
5. Evaluation 固定测试集：「我上周说过我喜欢什么咖啡 → 准确召回」类用例。
