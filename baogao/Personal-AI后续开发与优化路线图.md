# Personal AI 后续开发与优化路线图

> 项目路径：`E:\Pycharm\JQ\personal-ai`
> 当前阶段：P0–P6 已完成
> 文档目的：指导现有系统进入稳定使用、真实验证和按需求扩展阶段
> 编写日期：2026-08-21

---

## 1. 当前结论

项目已经完成本地单用户 Personal AI v1 的主体设计与开发，形成以下闭环：

```text
Chat
  → Context（Memory / RAG / Summary / Recent）
  → Model Gateway
  → Direct 或 Planned
  → Skill / Native Tool / MCP
  → Permission / Budget
  → Message / AgentRun / ToolRun / Plan 持久化
  → Web 实时展示
```

当前具备：

- SSE 流式聊天、会话管理和 AgentRun 生命周期；
- 长期记忆、会话摘要、敏感信息过滤和上下文预算；
- PDF、DOCX、TXT、Markdown 知识库；
- Vector + BM25 + RRF 混合检索和引用持久化；
- RAG 查询门控，只展示回答实际使用的 `[cN]` 来源；
- Native Tool、Skill、审批、ToolRun 和 stdio MCP；
- 一次性/周期 Activity、单 Worker、重启恢复；
- direct/planned 双模式、结构化 Planner、顺序步骤、一次有界 Replan；
- Plan、Activity、Capability 前端视图和只读 API。

当前验证基线：

```text
后端测试               87 passed, 1 skipped
RAG 固定集              Recall@1/3/5、MRR、章节、关键词均为 1.000
Planner 固定集          分类准确率 1.000，不安全工具提示数 0
前端                    npm run lint / npm run build 通过
```

因此，下一步不应立刻增加 P7 式大功能，而应先进入 **P6.1 稳定化与真实使用验证**。

---

## 2. 后续开发原则

1. **稳定优先于功能数量**：先消除真实模型、长会话、失败恢复和数据维护问题。
2. **以真实问题触发扩展**：没有指标证明需要时，不引入 DAG、多 Agent、Redis、向量数据库或插件市场。
3. **保持默认兼容**：Chat 和 Activity 默认仍为 `direct`，知识库默认自动门控。
4. **失败必须安全且可解释**：失败不能伪装成功，也不能因为自动修复而执行未经确认的动作。
5. **检索候选不等于回答来源**：只有正文实际引用的资料才能展示为来源。
6. **Planner 不能扩大权限**：重规划、格式修复和工具提示都不能绕过白名单、审批或预算。
7. **所有优化必须可验证**：每个改动必须有固定测试、指标或明确人工验收方法。

## 3. 当前最值得处理的问题

### 3.1 Planner 真实模型输出兼容性

已观察到规划模式可能出现：

```text
goal 必须是字符串
```

这表示模型返回的 Planner JSON 中 `goal` 缺失，或返回了数组、对象等非字符串类型。现有严格校验安全地停止了执行，这是正确行为，但用户体验还可以改进。

建议：

- 优先使用 Provider 支持的 JSON Schema / structured output；
- 在 Gateway 层统一结构化输出协议，不让业务层绑定具体模型参数；
- 不对非法计划进行本地猜测执行；
- 允许最多一次“仅格式化、不改变目标、不执行工具”的模型修复请求；
- 修复结果仍必须经过相同 schema、长度、步数和 allowed_tools 校验；
- 记录稳定错误码，如 `planner_invalid_goal`，前端显示友好说明；
- 提供“一键切换直接回答”，无需用户重新输入问题；
- 不保存隐藏推理或完整原始模型分析，只保存截断错误原因。

验收标准：

```text
合法 JSON                         正常执行
Markdown 代码块包裹 JSON          可解析
goal 缺失/对象/数组               安全失败或一次格式修复后成功
steps 超限/未知工具               必须失败，不能修复为越权计划
Provider 超时                     Plan 与 AgentRun failed
失败后点击直接回答                 使用原消息重新发起新的 direct Run
```

### 3.2 RAG 门控与来源语义

当前轻量门控已经解决计算、问候、时间/天气和纯写入任务乱带资料的问题，并且只有实际 `[cN]` 才显示来源。

近期只建议补足：

- 增加 `自动 / 使用知识库 / 不使用知识库` 请求级模式；
- 自动模式继续使用当前确定性规则；
- 强制知识库模式仍需相关性阈值，不能强行返回无关来源；
- 禁用模式不得生成 `rag.retrieved`；
- 未检索到资料时显示简短状态，而不是伪造来源；
- 未知 `[c99]` 从正文移除或转换为“无效引用”提示；
- 文档删除后，历史来源显示“资料已删除”，避免链接直接 404；
- 增加组合任务测试，例如“根据简历计算工作年限”。

暂不建议立即增加 Reranker。只有出现以下数据再引入：

```text
真实问题 Top-3 相关命中率持续低于 85%
知识库 chunk 数超过约 5 万
同主题文档过多导致 RRF 排序频繁错误
用户连续反馈“引用存在但不能支持结论”
```

### 3.3 错误信息和用户恢复路径

当前错误主要以技术字符串展示，例如 `goal 必须是字符串`。后续应把内部错误与用户提示分离。

建议建立有限错误码：

| 错误码 | 用户提示 | 可执行操作 |
|---|---|---|
| `planner_invalid_output` | 规划格式不符合要求，已停止执行 | 重试规划 / 直接回答 |
| `planner_budget_exhausted` | 已达到本次任务执行上限 | 缩小目标 / 查看步骤 |
| `tool_rejected` | 操作需要授权或后台禁止执行 | 查看工具记录 |
| `rag_no_evidence` | 当前资料库中没有找到可靠依据 | 继续普通回答 / 上传资料 |
| `provider_unavailable` | 模型服务暂时不可用 | 稍后重试 |
| `run_conflict` | 当前会话已有任务运行中 | 等待 / 停止当前任务 |

错误响应中不得返回 API Key、MCP command、绝对沙箱路径、完整 Prompt 或完整 Tool Result。

### 3.4 可观察性不足

现有 ToolRun、AgentRun、Plan 已提供数据基础，但还缺少统一运行诊断。

建议增加只读运行详情：

```text
Run 状态与 execution_mode
Plan 版本和步骤耗时
模型轮次与 token usage
工具调用次数、耗时、状态
是否触发 RAG、候选数、实际引用数
失败阶段和稳定错误码
```

前端只展示用户可理解的信息；完整诊断只进入开发日志，不展示敏感参数。

## 4. 推荐开发阶段

## 4.1 P6.1：稳定化与用户体验

优先级：**立即执行**。

建议工作量：1–2 个短迭代。

| 编号 | 内容 | 优先级 | 验收 |
|---|---|---:|---|
| S1 | Planner structured output 与一次安全格式修复 | P0 | 真实模型异常不再直接暴露技术字段错误 |
| S2 | 规划失败“一键直接回答” | P0 | 原问题可重新以 direct 运行，不复用失败 Run |
| S3 | RAG 自动/强制/禁用三态 | P1 | 每种模式都有 API、前端和测试 |
| S4 | 未知引用和已删除来源处理 | P1 | 不出现可点击的伪来源或裸 `[c99]` |
| S5 | 用户错误码与恢复操作 | P1 | 常见失败均有明确下一步 |
| S6 | Run 诊断摘要 | P1 | 可定位 Planner、RAG、Tool、Provider 失败阶段 |
| S7 | 真实使用回归集 | P0 | 至少 50 条中文真实任务固定化 |

P6.1 完成后，项目才进入持续日常使用状态。

## 4.2 P6.2：数据与部署可靠性

优先级：**真实数据开始长期积累后执行**。

### 数据维护

- SQLite 自动备份、备份保留数和恢复脚本；
- 上传原文件与数据库一致性检查；
- 清理孤立文件、孤立 chunk 和失效 citation；
- 数据库 schema 版本表；
- 迁移前自动备份；
- 超长会话归档和 Activity 历史保留策略。

### 服务可靠性

- `/health/live` 与 `/health/ready`；
- Provider、Embedding、MCP 启动状态诊断；
- 优雅关闭等待当前 direct Run，取消或安全收尾 Activity；
- 日志轮转和错误采样；
- Windows 本地启动/停止脚本；
- 固定依赖版本与离线部署说明。

### 性能基线

需要记录而不是猜测：

```text
首 token 延迟
完整回答耗时
Planner 额外延迟
RAG 检索 P50/P95
Embedding 入库速度
数据库大小与 chunk 数
每个 Run 的模型/工具调用数
```

只有检索 P95 或数据库规模达到明确瓶颈后，才评估 PostgreSQL、pgvector 或专用向量数据库。

## 4.3 P6.3：单用户能力扩展

优先级：**按个人使用需求选择**。

推荐顺序：

1. 联网搜索与网页正文提取；
2. 天气、地图或旅行信息等只读实时 Tool；
3. 日历查询与创建事件；
4. 邮件草稿，发送必须逐次审批；
5. Todo/提醒同步；
6. 图片 OCR 和扫描 PDF；
7. 更丰富的文档导出，如 Markdown、DOCX、PDF。

每个外部能力必须具备：

```text
明确来源
最小权限
固定风险等级
请求级白名单
超时与结果上限
ToolRun 审计
凭据不进入 Prompt、事件和日志
写操作可预览并审批
```

## 5. 暂不建议开发的内容

### 5.1 Multi-Agent

当前共享 Executor 已能完成顺序复杂任务，没有证据表明需要多个角色 Agent。Multi-Agent 会增加上下文重复、成本、权限传播和调试难度。

触发门槛：单 Agent 在固定复杂任务集上持续因角色上下文冲突失败，且不能通过有限步骤或工具改善。

### 5.2 通用 DAG 或工作流画布

当前 Plan 是 2–6 个顺序步骤，符合个人助手主要任务。DAG 会引入依赖解析、并行写操作、部分失败回滚和复杂 UI。

触发门槛：真实任务中至少 20% 无法用顺序步骤稳定表达。

### 5.3 自主创建 Activity

当前 Activity 由用户拥有和创建，这是正确安全边界。Agent 不应自行建立长期目标或周期任务。

触发门槛：先设计 Goal 配额、用户确认、撤销、到期和通知机制，再考虑有限开放。

### 5.4 插件市场和在线代码安装

Capability Registry 当前只读即可。在线插件需要来源信任、签名、权限 manifest、依赖隔离、升级和回滚，不能把下载代码包装成简单开关。

### 5.5 分布式 Worker

当前单用户、单 Worker 没有容量证据。不要提前引入 Redis、队列系统或分布式锁。

## 6. 测试与评测扩展

### 6.1 真实任务集

建议新增 `tests/eval/real_tasks.json`，至少覆盖：

```text
10 条直接问答/闲聊
10 条知识库问答与无资料问题
10 条工具与审批任务
10 条 planned 多步骤任务
5 条 planned Activity
5 条恶意 Prompt、越权工具和引用注入
```

### 6.2 建议指标

| 类型 | 指标 |
|---|---|
| Chat | 首 token、完成率、direct 兼容率 |
| RAG | 路由准确率、Recall@K、引用支持率、无关来源展示数 |
| Planner | Schema 成功率、步骤完成率、Replan 率、预算违规数 |
| Tool | 成功率、审批等待、越权执行数、重复写操作数 |
| Activity | 到期执行率、重启恢复率、重复执行率 |
| Data | 孤立记录数、备份成功率、恢复成功率 |

安全硬指标：

```text
越权工具执行数                    必须为 0
后台 high 工具实际执行数           必须为 0
未知引用附带来源卡片数             必须为 0
Prompt / 事件 / 日志凭据泄漏数      必须为 0
同会话并发 running Run             必须为 0
```

## 7. 建议实施顺序

### 迭代 A：Planner 稳定性

```text
structured output
→ 一次安全格式修复
→ 错误码
→ 一键直接回答
→ 真实 Provider 契约测试
```

### 迭代 B：RAG 与引用体验

```text
自动/强制/禁用模式
→ 未知引用处理
→ 已删除来源状态
→ 组合问题回归集
```

### 迭代 C：运行诊断与数据维护

```text
Run 诊断 API/UI
→ health check
→ 备份恢复
→ 孤立数据扫描
→ 性能基线
```

### 迭代 D：按需外部能力

根据实际个人需求，从联网搜索、天气、日历、邮件草稿中选择一个能力完成完整 Tool 安全闭环，不并行堆叠多个连接器。

## 8. P6.1 完成标准

```text
□ 真实模型 Planner 格式异常有安全且友好的恢复路径
□ 规划失败可以一键切换 direct，且产生新的独立 AgentRun
□ RAG 支持自动/强制/禁用三种请求模式
□ 未实际引用、未知引用和已删除资料不会显示为正常来源
□ 用户错误与内部错误分离，不泄漏敏感配置
□ 可以查看一次 Run 的阶段、耗时、预算和失败位置
□ 至少 50 条真实中文任务形成固定回归集
□ 后端全量测试、RAG/Planner 评测和前端构建全部通过
□ 有可验证的 SQLite 备份与恢复流程
```

## 9. 最终建议

当前项目功能主体已经完整，下一阶段的价值不在于继续增加概念，而在于：

```text
真实使用
  → 收集失败样本
  → 固定成测试
  → 修复最常见问题
  → 建立备份和诊断
  → 再按需求增加一个外部能力
```

推荐把后续阶段命名为 **P6.1 稳定化与体验优化**，而不是直接进入 P7。完成 Planner 真实模型兼容、RAG 三态、错误恢复、运行诊断和数据备份后，再根据真实指标决定是否需要更复杂的 RAG、外部连接器、工作流或部署架构。
