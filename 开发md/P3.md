# P3 阶段开发文档：开始做事（最小可交付版）

> 项目：`E:\Pycharm\JQ\personal-ai`  
> 前提：P0（聊天）、P1（记忆）、P2（RAG）已完成  
> 目标：让 Agent 能安全调用少量本地工具，高风险写入由用户确认，执行过程可见、可查。  
> 版本：v3（复杂度收敛版）

---

## 1. 设计原则

P3 只建立后续阶段可以复用的最小工具执行链，不追求完整权限平台。

```text
模型决定调用工具
  -> 后端校验工具和参数
  -> 固定风险等级判断
  -> 必要时等待用户审批
  -> 执行工具并记录结果
  -> 把工具结果交回模型生成最终回答
```

本阶段优先级：

1. 主流程可运行；
2. 文件工具不逃出沙箱；
3. 高风险操作必须确认；
4. 不破坏 P0-P2；
5. 暂不为多进程、多用户和服务重启设计复杂状态机。

| 多用户权限、审批持久化、跨进程恢复 | 后续按部署需求决定 |
| 服务重启后恢复待审批 Run | P3 待审批状态仅保存在单进程内存 |
| Planner / Replanning | P6 |
| 定时任务 / 自主 Activity | P5 |
| OpenTelemetry / 完整监控平台 | P3 使用数据库记录和日志即可 |
| Query Rewrite / Reranker / OCR | 不属于 P3 |

**完成边界**：用户提问能触发工具；读取限制在沙箱；写入必须确认；前端能看到执行状态；数据库能查到工具记录。

## 4. Tool 设计

### 4.1 Tool 契约

```python
@dataclass
class Tool:
    name: str
    description: str
    input_schema: dict
    risk_level: str       # low | medium | high，P3 固定值
    timeout: float

    async def run(self, args: dict) -> str:
        ...
```

工具注册表保持简单：

```python
TOOLS: dict[str, Tool] = {}

async def execute_tool(name: str, args: dict, allowed_tools: set[str]) -> str:
    # 校验白名单 -> 校验参数 -> 超时执行 -> 截断结果 -> 错误转文本
    ...
```

不增加 Manager、Service、Executor 等额外层。

### 4.2 Native Tools

| 工具 | 风险 | 行为 |
|---|---|---|
| `get_time` | low | 返回当前日期、时间和配置时区 |
| `calculate` | low | 安全计算简单数学表达式 |
| `read_file` | medium | 读取 `SANDBOX_DIR` 内的 UTF-8 文本文件 |
| `write_file` | high | 新建或覆盖沙箱内 UTF-8 文本文件，执行前一律审批 |

`write_file` 不根据“文件是否存在”动态改变风险。所有写入统一为 high，可以少做一套动态风险和竞态处理，也保证不会未经确认覆盖文件。

P3 的 `write_file` 只接受：

```json
{"path": "notes.md", "content": "..."}
```

- 写入完整替换目标文件内容；
- 默认不创建父目录；
- 沙箱根目录在应用启动时创建；
- 禁止目标为目录、符号链接或其他非常规文件；
- 不提供 append、delete、move、rename，后续需要时再增加独立工具。

### 4.3 安全约束

安全上限放在 `core/tools.py` 模块常量中，不做成大量环境变量：

```text
MAX_EXPRESSION_CHARS = 200
MAX_AST_DEPTH = 8
MAX_FILE_READ_BYTES = 64 * 1024
MAX_FILE_WRITE_BYTES = 1024 * 1024
MAX_TOOL_RESULT_CHARS = 4000
```

必须实现：

```text
□ calculate 只允许数字、四则运算、括号及有限的幂运算
□ 禁止名称、调用、属性访问、下标、import 和 eval
□ 限制表达式长度、AST 深度、指数和结果大小
□ 文件路径 resolve 后必须仍位于 SANDBOX_DIR 内
□ 拒绝绝对路径、路径逃逸、目录和符号链接
□ 文件大小按 UTF-8 字节数计算
□ malformed JSON、未知字段、缺失字段返回工具错误文本
□ 单工具超时后返回 timeout 结果，不让整个 Run 崩溃
□ 工具输出截断后注明“结果已截断”
```

工具错误作为 `role=tool` 的结果交回模型，由模型向用户解释；只有 Agent Runtime 自身故障才触发 `run.failed`。

## 5. Skill 设计

### 5.1 示例 Skill

```text
skills/
├── time-helper/SKILL.md
└── file-notes/SKILL.md
```

```markdown
---
name: file-notes
description: 读取和保存沙箱中的文本笔记
required_tools: [read_file, write_file]
enabled: true
---
需要了解已有内容时先读取；需要保存内容时调用 write_file。
写入操作会由系统请求用户确认。
```

### 5.2 加载规则

```text
应用启动时扫描 skills/*/SKILL.md
  -> 解析 frontmatter 和正文
  -> 只加载 enabled: true
  -> required_tools 必须已注册，否则跳过该 Skill 并记录错误日志
```

P3 不做按意图动态选择 Skill。“本次启用 Skill”明确指：请求开始时全部全局 `enabled: true` Skill 的只读快照。

### 5.3 工具白名单

```text
已注册工具：TOOLS 中的全部工具，但不等于模型可见
默认暴露工具：get_time + calculate
请求暴露工具：默认暴露 + 全部启用 Skill 的 required_tools
```

规则：

1. disabled Skill 不注入指令，也不贡献工具；
2. 模型只收到请求白名单内的 tools schema；
3. Tool Router 再检查一次白名单，阻止模型或 Provider 伪造调用；
4. Skill 指令在 `build_context()` 中加入 System，并计入上下文预算。

## 6. Gateway 与 Tool Calling 协议

### 6.1 保持现有契约

```text
complete(messages, ...) -> str
```

该方法继续供摘要和记忆提取使用，P3 不修改返回类型，也不新增暂时没有调用方的 `complete_with_tools()`。

只扩展流式方法：

```python
async def stream(
    messages: list[dict],
    temperature: float = 0.7,
    tools: list[dict] | None = None,
) -> AsyncIterator[StreamChunk]:
    ...
```

`StreamChunk` 增加 `tool_calls_delta` 字段。Agent 按 `tool_calls[].index` 拼接 `id`、`name` 和 `arguments`。

### 6.2 正确的消息序列

模型产生工具调用后，必须先追加带 `tool_calls` 的 assistant 消息，再追加工具结果：

```text
messages
  + assistant(content, tool_calls=[...])
  + tool(tool_call_id=<原始 id>, content=<执行结果>) × N
  -> 下一轮 LLM
```

要求：

- `tool_call_id` 原样回传，不重新生成；
- 多个 tool call 按模型返回顺序依次执行和追加；
- 工具参数 JSON 在流结束后统一解析和校验；
- 中间工具回合的文本通常为空；若模型输出了少量过程文本，作为说明正常展示，不撤回。

### 6.3 MockProvider

Mock 行为保持确定性：

```text
输入含“时间/几点”       -> get_time
输入含“计算”            -> calculate
输入含“读取文件/查看笔记” -> read_file
输入含“写入/保存笔记”    -> write_file
最后一条消息 role=tool   -> 根据工具结果生成最终回答
其他输入                 -> 现有 Mock 文本回答
```

Mock 只能选择本次 `tools` 参数中实际存在的工具。

## 7. Agent 多步循环

每个 LLM 回合保持现有流式输出（`message.delta` 边收边发，不缓存整回合）；若回合出现 `tool_calls`，其文本内容通常为空（Mock 与真实模型均如此），已发出的少量文本作为过程说明保留，无需撤回。工具调用增量按 `tool_calls[].index` 并行拼接。

```text
1. 构建上下文、Skill 快照和工具白名单
2. 调用 LLM，流式输出文本（若有），同时拼接 tool_calls 增量
3. 没有 tool_calls：回合即最终回答，正常结束
4. 有 tool_calls：
   a. 追加 assistant(tool_calls)
   b. 按顺序处理每个工具
   c. 追加对应 role=tool 消息
   d. 进入下一轮 LLM
5. 达到 AGENT_MAX_STEPS：输出固定的步骤上限提示并结束
6. 最终回答保存后，沿用现有记忆提取与会话摘要后处理（不改动）
```

### 7.1 计数定义

```text
round_index：LLM 回合编号，仅在运行时使用，从 0 开始
step_index：工具调用的全局顺序，从 0 开始；每执行或拒绝一个工具递增一次
```

因此同一 LLM 回合产生多个工具时，每个 `tool_runs` 仍有唯一、稳定的 `step_index`，不需要额外的 `call_index`。

`AGENT_MAX_STEPS` 表示允许的最大 LLM 回合数，包括最后生成自然语言回答的回合。达到上限时不再调用模型，由 Agent 输出固定提示并正常保存。

### 7.2 Token 与上下文

- `run.completed.token_usage` 累计全部 LLM 回合；
- `agent_runs` 保存累计 input/output tokens；
- 工具结果经过长度截断后再加入 messages；
- P3 不在每轮重新检索 Memory/RAG，只复用本次 Run 初始上下文。

## 8. Permission 与 Approval

### 8.1 固定风险等级

```text
low       get_time / calculate     自动执行
medium    read_file                自动执行并记录
high      write_file               必须审批
```

风险等级完全由 Tool 定义，不由模型或文件状态决定。

### 8.2 审批流程

```text
模型请求 write_file
  -> 后端完成白名单和参数校验
  -> 创建 tool_runs(status=pending_approval)
  -> 创建 approval_id 和内存 waiter
  -> 发 approval.required
  -> 等待用户批准、拒绝或超时
     -> 批准：发 approval.completed，再发 tool.started 并执行
     -> 拒绝：发 approval.completed + tool.completed(rejected)
     -> 超时：按拒绝处理，status=timeout
  -> 将结果作为 role=tool 回传模型
```

事件顺序中，`tool.started` 只表示工具真正开始执行，不能在审批前发送。

### 8.3 简化的内存 waiter

```python
APPROVAL_WAITERS: dict[str, ApprovalWaiter] = {}
# approval_id -> {run_id, event, approved}
```

P3 约束：

- 单进程、单用户使用；
- waiter 以 `approval_id` 为键；
- `try/finally` 保证批准、拒绝、超时、异常或 SSE 取消时移除 waiter；
- API 使用原子状态检查，第一次有效提交成功；
- 已处理、已超时或未知的 approval_id 统一返回 `404`，不保留额外终态缓存；
- 应用关闭时唤醒并拒绝所有 waiter；
- 未完成的 AgentRun 标记为 failed 或 cancelled，不永久停留在 running。

### 8.4 超时

审批等待计入 Run 总超时，不实现暂停计时。

```env
APPROVAL_TIMEOUT_SECONDS=60
AGENT_TIMEOUT_SECONDS=180
```

外层 `AGENT_TIMEOUT_SECONDS` 覆盖整个主流程；审批内部单独使用 60 秒超时。默认配置确保审批先结束，并为后续模型回答留出时间。

## 9. Observability

### 9.1 tool_runs 表

```python
class ToolRun(Base):
    __tablename__ = "tool_runs"

    id
    run_id
    conversation_id
    tool_call_id
    step_index
    tool
    args_summary
    result_summary
    risk_level
    approval_id
    approved_at
    status          # pending_approval | running | completed | rejected | failed | timeout
    duration_ms
    created_at
    completed_at
```

同一 Run 内 `step_index` 每个工具调用递增，因此可按 `(run_id, step_index)` 稳定还原执行顺序。

参数和结果只保存截断摘要；不保存完整文件内容。日志包含：

```text
run_id / step_index / tool / risk_level / status / duration_ms
```

P3 不实现完整追踪平台。`GET /api/runs/{run_id}` 为可选调试接口，不作为完成阻塞项。

## 10. SSE 与前端

### 10.1 事件

```text
run.started
agent.status
tool.started
tool.completed
approval.required
approval.completed
message.delta
message.completed
run.completed
run.failed
```

数据结构：

```text
agent.status       {status, tool?}
tool.started       {run_id, step_index, tool, args_summary}
tool.completed     {run_id, step_index, tool, result_summary, status}
approval.required  {approval_id, run_id, tool, args_summary, risk_level}
approval.completed {approval_id, run_id, tool, approved}
```

写入批准的典型顺序：

```text
run.started
-> approval.required
-> approval.completed(approved=true)
-> tool.started
-> tool.completed(completed)
-> message.delta...
-> message.completed
-> run.completed
```

### 10.2 前端

`ChatView.tsx`：

- 显示“正在调用工具：工具名”；
- 显示成功、失败、拒绝和超时状态；
- 收到 `approval.required` 时显示确认卡片；
- 防止同一审批按钮重复点击；
- 请求失败后允许重试审批，但 404 时显示“审批已失效”；
- 用户点击停止时中止 SSE，后端负责清理 waiter。

## 14. 验收标准

```text
□ “现在几点”调用 get_time，并基于结果回答
□ “计算 12*(3+4)”调用 calculate，禁止执行任意代码
□ read_file 只能读取沙箱内 UTF-8 文本
□ write_file 每次执行前都出现审批卡片
□ 批准后写入，拒绝或超时后不写入
□ 工具协议包含 assistant.tool_calls -> tool(tool_call_id)
□ 工具参数错误和执行错误不会导致整个 Run 崩溃
□ 达到 AGENT_MAX_STEPS 后正常结束并保存固定提示
□ tool_runs 按 step_index 记录风险、状态、耗时和摘要
□ disabled Skill 不注入指令、不暴露工具
```
