# P5 阶段开发文档：主动工作（Activity 最小闭环版）

> 项目：`E:\Pycharm\JQ\personal-ai`
>
> 前提：P0-P4 已完成（聊天、记忆、RAG、Tool/Skill/审批、stdio MCP）
>
> 目标：让用户可以创建一次性或周期 Activity，由应用在后台按时运行现有 Agent，并查看状态与结果。
>
> 版本：v1（复杂度收敛版）

---

## 1. 设计原则

P5 只建立一条可持久化、可恢复、可观察的后台执行链，不建设分布式任务平台。

```text
用户创建 Activity
  -> SQLite 保存计划
  -> 单进程 Worker 轮询到期记录
  -> 复用现有 Agent Runtime
  -> 复用 Skill / Tool / MCP / ToolRun
  -> 结果写入 Activity 对应会话
  -> Activity 页面展示状态和历史
```

必须遵守：

1. Activity 不能建立第二套 Agent、Tool Router、Skill、权限或观测系统；
2. 计划和运行状态必须持久化，应用重启后不能静默丢失；
3. 后台没有在线审批上下文，高风险工具一律拒绝，不能自动批准；
4. P5 只支持单进程、单 Worker，不宣称支持多实例并发；
5. 简单优先，不引入 Redis、Celery、APScheduler、WebSocket、Event Bus；
6. P5 不做 Planner、自然语言拆解、自治循环或第三方通知，这些属于 P6 或真实需求扩展。

### Activity 的定位

```text
Chat：用户在线发起一次 Agent Run，并实时接收 SSE
Activity：用户预先保存一个提示词，由后台在指定时间发起 Agent Run
```

P5 的“主动”表示应用可以在用户没有保持聊天连接时按计划执行，不表示 Agent 可以自行创建目标、修改计划或无限运行。

## 2. 范围

### 2.1 包含

```text
Activity CRUD      创建、列表、暂停、恢复、立即运行、删除
Schedule           一次性时间 / 固定分钟间隔
Persistence        SQLite 保存计划、状态和最近一次结果
Worker             FastAPI lifespan 内一个后台协程串行执行
Recovery           启动时恢复中断的 running Activity
Agent Reuse        后台调用现有 run_chat，不复制 Agent Loop
Safety             high 工具立即拒绝，不创建无人等待的审批
Observability      AgentRun.activity_id + 现有 ToolRun + Activity 最近状态
Frontend           第四个“活动”主视图，管理计划并跳转结果会话
Tests              调度、执行、恢复、安全、API、前端构建和全量回归
```

### 2.2 不做

| 内容 | 原因 / 去向 |
|---|---|
| Redis / Celery / RQ / Dramatiq | 单机阶段没有分布式队列需求 |
| 独立 `apps/worker` 进程 | 会引入部署、锁、MCP 生命周期和 Provider 配置重复 |
| cron 表达式和复杂日历规则 | P5 只支持一次性和固定间隔 |
| 自然语言“每天九点提醒我”的自动建任务 | 先用明确表单验证任务闭环 |
| Event Trigger / Webhook | 等有真实事件来源后再增加 |
| 邮件、系统通知、浏览器推送 | 结果先进入应用内会话和 Activity 页面 |
| 多 Worker、分布式锁、抢占和优先级 | P5 固定一个串行 Worker |
| 自动重试和指数退避 | 失败可手动立即运行；周期任务等下个周期 |
| catch-up 补跑所有错过周期 | 重启后最多补跑一次，避免任务风暴 |
| 后台等待用户审批 | high 工具直接拒绝并留下 ToolRun 记录 |
| Activity 自行创建或修改 Activity | 禁止自治扩散 |
| Planner / Replanning / Autonomous Activity | P6 |
| 新的消息队列、事件表或审计表 | SQLite Activity 状态 + AgentRun/ToolRun 已足够 |

**完成边界**：用户创建一次性或周期 Activity 后，即使没有打开聊天 SSE，应用也能在到期时执行；结果进入专属会话；可暂停、恢复、立即运行和查看状态；重启后计划仍存在；后台 high 工具不会执行。

## 4. 最小架构

P5 不创建通用 Queue 接口。`activities` 表本身就是当前阶段的持久化计划和队列。

```text
POST /api/activities
  -> Activity(status=scheduled, next_run_at=...)

Activity Worker（单协程）
  -> 查询最早到期的 scheduled Activity
  -> 原子地改为 running
  -> run_chat(..., activity_id=id, approval_mode="deny")
  -> 消费 AgentEvent，但不建立第二条 SSE
  -> 更新 Activity 和下一次执行时间
```

只允许一个进程运行 Worker。P5 的开发和部署命令不得使用多个 Uvicorn worker：

```powershell
uv run uvicorn apps.api.main:app --port 8787
```

`--reload` 仅用于开发；重载过程可能终止当前 Run，启动恢复逻辑必须能够处理。

## 5. 数据模型

### 5.1 Activity

在 `infrastructure/database.py` 新增：

```python
class Activity(Base):
    __tablename__ = "activities"

    id: Mapped[str]
    user_id: Mapped[str]
    conversation_id: Mapped[str]
    title: Mapped[str]
    prompt: Mapped[str]
    schedule_type: Mapped[str]       # once | interval
    interval_minutes: Mapped[int | None]
    next_run_at: Mapped[datetime]
    status: Mapped[str]              # scheduled | running | paused | completed | failed
    last_run_id: Mapped[str | None]
    last_error: Mapped[str | None]
    last_started_at: Mapped[datetime | None]
    last_completed_at: Mapped[datetime | None]
    created_at: Mapped[datetime]
    updated_at: Mapped[datetime]
```

约束：

```text
title                  1..200 字符
prompt                 1..4000 字符
schedule_type          once | interval
once                   interval_minutes 必须为空
interval               interval_minutes 必须在 1..10080
next_run_at             API 必须接收带时区 ISO 8601，入库统一 UTC
last_error              最多保存 1000 字符
```

SQLite 读取 `DateTime(timezone=True)` 时仍可能返回无 `tzinfo` 的值。P5 在数据库边界把这类值明确视为 UTC，比较前统一规范化，API 序列化时输出带 `+00:00` 的时间；禁止混用本地 naive datetime。

不增加 `ActivityRun` 表。每次实际执行已经产生 `AgentRun`；通过 `AgentRun.activity_id` 查询历史，避免重复保存运行状态。

### 5.2 AgentRun 关联

给 `AgentRun` 增加：

```python
activity_id: Mapped[str | None] = mapped_column(
    String(32), nullable=True, index=True
)
```

不增加数据库外键：

- 删除 Activity 后保留既有 AgentRun / ToolRun / Message；
- 现有项目的 Message、AgentRun 也没有 Conversation 外键；
- P5 不单独引入级联删除复杂度。

### 5.3 SQLite 兼容迁移

`Base.metadata.create_all()` 会创建 `activities`；已有 `agent_runs` 需要 `_migrate_sqlite_p5()`：

```text
检查 agent_runs 是否存在 activity_id
  -> 不存在时 ALTER TABLE ADD COLUMN activity_id VARCHAR(32)
  -> CREATE INDEX IF NOT EXISTS ix_agent_runs_activity_id
```

迁移必须可重复执行。P5 不引入 Alembic。

## 6. 调度语义

### 6.1 一次性任务

```text
scheduled -> running -> completed
                     -> failed
```

失败后不自动重试。用户可以点击“立即运行”，将其重新设为 `scheduled` 且 `next_run_at=now`。

### 6.2 周期任务

```text
scheduled -> running -> scheduled(next occurrence)
```

无论本次成功还是失败，周期 Activity 都进入下个周期；本次结果通过 `last_run_id`、`last_error` 和 AgentRun 历史查看。

下一次时间以原 `next_run_at` 为基准不断增加 `interval_minutes`，直到严格晚于当前时间：

```text
next = previous_next + interval
while next <= now:
    next += interval
```

这样重启或长时间停机后最多执行一次到期任务，不补跑所有错过周期。

### 6.3 暂停、恢复和立即运行

```text
pause    scheduled -> paused
resume   paused -> scheduled；next_run_at 保留，若已过期则会尽快执行一次
run-now  scheduled/completed/failed -> scheduled(next_run_at=now)
delete   running 时返回 409；其他状态删除 Activity，保留会话和运行历史
```

运行中的 Activity P5 不支持强制终止。应用关闭时统一取消当前 Worker Run。

## 7. Worker（core/activity.py）

保持一个扁平模块，不创建 `activity/` 包、Manager、Repository、Queue Adapter 或 Scheduler Factory。

建议公开的最小函数：

```python
async def activity_worker(
    stop_event: asyncio.Event,
    provider,
    embedding_provider,
    skills: list[Skill],
) -> None: ...

def recover_interrupted_activities() -> int: ...
```

内部函数只负责：

```text
_claim_due_activity()      领取一个到期 Activity，并提交 running
_run_activity()            消费 run_chat 事件，捕获 run_id/完成/失败
_finish_activity()         写回状态、错误和下次时间
```

### 7.1 轮询

```text
没有到期任务 -> 等待 ACTIVITY_POLL_SECONDS 或 stop_event
领取到任务   -> 串行执行，完成后继续查询
数据库异常   -> 记录 exception，等待下一轮，不退出整个应用
```

禁止无间隔死循环。等待必须可被 shutdown 的 `stop_event` 立即唤醒。

### 7.2 领取边界

单进程模式下使用一次短事务：

```text
SELECT 最早的 scheduled AND next_run_at <= now
UPDATE status=running, last_started_at=now, last_error=NULL
COMMIT
```

P5 不实现多进程 `SELECT FOR UPDATE SKIP LOCKED`。README 和日志必须明确单 Worker 边界。

### 7.3 启动恢复

应用非正常退出可能留下 `running`。启动 Worker 前：

```text
running -> scheduled
next_run_at -> min(原时间, now)
last_error -> "上次运行被服务重启中断，已重新排队"
```

这是 at-least-once 恢复，不承诺 exactly-once。因为后台 high 工具被禁止，恢复重跑不会自动执行高风险写操作。

## 8. 复用 Agent Runtime

### 8.1 run_chat 最小扩展

只增加两个可选参数：

```python
async def run_chat(
    ...,
    activity_id: str | None = None,
    approval_mode: Literal["interactive", "deny"] = "interactive",
) -> AsyncIterator[AgentEvent]:
```

默认值必须保证既有聊天 API 和测试行为不变。

- `activity_id` 写入本次 `AgentRun`；
- `interactive` 沿用 P3 审批流程；
- `deny` 遇到 high 工具时直接写入 `ToolRun(status="rejected")`，把“后台任务不能执行需要用户审批的工具”作为工具结果交回模型；
- `deny` 不调用 `create_approval()`，不产生永远无人处理的 waiter，也不等待超时。

不要复制 `run_chat` 或抽出新的通用 Executor。P5 的后台执行仍然经过同一个 Context、Gateway、Skill 白名单、Tool Router、MCP 和持久化流程。

### 8.2 后台事件处理

Worker 消费 `run_chat` 产生的事件：

```text
run.started    -> 保存 Activity.last_run_id
run.completed  -> 本次成功
run.failed     -> 本次失败并保存 error
其他事件       -> 不实时推送；其持久化结果仍在 Message / ToolRun
```

P5 不新增 Activity SSE，不缓存全部事件，不把隐藏推理写入数据库。

### 8.3 会话

创建 Activity 时由后端同时创建专属 Conversation：

```text
Conversation.title = "活动：{title}"（受 200 字符限制）
Activity.conversation_id = Conversation.id
```

Conversation 和 Activity 必须在同一个数据库事务中创建；任一校验或提交失败时整体回滚，不能留下孤立会话。

每次运行把 Activity.prompt 作为用户消息写入该会话，助手结果紧随其后。Activity 页面提供“查看会话”，复用现有 ChatView，不另做结果详情渲染器。

删除 Activity 不删除会话和消息。删除仍被 Activity 引用的会话返回 `409`，用户需先删除 Activity，避免 Worker 指向不存在的会话。

### 8.4 记忆和摘要

后台 Activity 可以读取现有 Memory 和 RAG。为避免周期提示词被反复提取为用户记忆，`run_chat` 再增加开关会扩大接口，P5 暂采用以下最小规则：

```text
activity_id is not None -> 跳过自动 Memory 提取
                       -> 保留会话摘要更新
```

该判断直接使用已有 `activity_id`，不增加第三个参数。

## 9. 安全与权限

### 9.1 后台工具策略

| 风险 | 后台行为 |
|---|---|
| low | 按现有白名单和参数校验执行 |
| medium | 按现有规则执行；当前仅为沙箱读取 |
| high | 立即拒绝，不创建审批、不执行 |

工具风险仍由 `Tool.risk_level` 固定定义。Activity 不能通过请求参数降低风险等级。

### 9.2 创建权限边界

P5 仍是单用户应用，API 沿用 `user_id="default"`。必须限制：

```text
最大标题/提示词长度
最小周期 1 分钟
最多活动数量 100（模块常量，不增加环境变量）
带时区时间校验
运行中禁止删除、暂停或重复领取
```

Activity 的 prompt 是模型输入，不是系统指令；Character、系统安全规则和 Skill 指令仍具有更高优先级。

## 11. API

新建 `apps/api/activities.py`，路由前缀 `/api/activities`。

| 方法 | 路径 | 行为 |
|---|---|---|
| `GET` | `/api/activities` | 按创建时间倒序返回 Activity |
| `POST` | `/api/activities` | 创建 Activity 和专属 Conversation |
| `GET` | `/api/activities/{id}` | Activity 详情 |
| `GET` | `/api/activities/{id}/runs` | 返回关联 AgentRun 历史 |
| `POST` | `/api/activities/{id}/pause` | 暂停 scheduled Activity |
| `POST` | `/api/activities/{id}/resume` | 恢复 paused Activity |
| `POST` | `/api/activities/{id}/run-now` | 立即排队执行 |
| `DELETE` | `/api/activities/{id}` | 非 running 状态删除 Activity |

创建请求：

```json
{
  "title": "每日资料总结",
  "prompt": "总结知识库中最近加入的资料，列出三条重点。",
  "schedule_type": "interval",
  "interval_minutes": 1440,
  "next_run_at": "2026-08-22T09:00:00+08:00"
}
```

响应必须使用带时区 ISO 8601。非法状态转换返回 `409`，不存在返回 `404`，字段错误返回 `422`。

P5 不提供任意修改 `status` 的 PATCH，避免前端直接伪造运行状态。

## 13. 生命周期

FastAPI lifespan 启动顺序：

```text
1. init_db（包含 P5 迁移）
2. 创建 sandbox
3. 构建 LLM Provider
4. 构建 Embedding Provider
5. 连接 MCP 并注册工具
6. load_skills
7. ACTIVITY_ENABLED=true 时恢复中断 Activity
8. 创建 stop_event 和 activity worker task
9. 接受请求
```

关闭顺序：

```text
1. 设置 activity stop_event
2. 取消并等待 Worker；当前 AgentRun 走 cancelled 收尾
3. 拒绝聊天侧待审批 waiter
4. 注销并关闭 MCP
5. 关闭 LLM Provider
6. 关闭 Embedding Provider
```

Worker 必须在 MCP 和 Provider 前关闭，否则后台 Run 可能访问已释放资源。

`app.state.activity_stop_event` 和 `app.state.activity_task` 只保存当前 lifespan 实例，不创建无归属的全局任务。

## 14. 错误与恢复边界

```text
模型/API 错误            AgentRun failed，Activity 记录 last_error
工具失败                 沿用 ToolRun；Agent 可基于失败结果继续回答
high 工具                rejected，不执行，Activity 可正常生成说明性结果
数据库暂时异常           Worker 记录日志并在下次轮询重试
Conversation 不存在      Activity failed，不自动创建替代会话
应用正常关闭             当前 Run cancelled；Activity 启动时重新排队
应用崩溃                 running 在下次启动恢复为 scheduled
周期任务执行时间过长     串行 Worker 导致后续任务延迟，不并发补跑
```

P5 接受串行任务延迟，这是用简单、可调试性换取的明确边界。当真实任务量证明单 Worker 不够，再评估独立 Worker 和数据库抢占。

## 17. 验收标准

```text
□ Activity 和 AgentRun.activity_id 已持久化，旧 SQLite 可兼容升级
□ 支持 once 和 interval 两种明确调度方式
□ 到期 Activity 在没有聊天 SSE 连接时也能运行
□ Worker 固定单协程串行执行，不引入外部队列依赖
□ 一次性任务成功后 completed，失败后 failed
□ 周期任务执行后只安排一个未来周期，不产生补跑风暴
□ 应用重启后 running Activity 能恢复排队
□ 后台 Run 复用现有 Context、Gateway、Skill、Tool、MCP 和 ToolRun
□ 后台 high 工具立即 rejected，且不存在审批 waiter 泄漏
□ Activity Run 不重复提取用户 Memory
□ 结果写入专属 Conversation，并可从 Activity 页面跳转查看
□ 用户可以创建、暂停、恢复、立即运行和删除 Activity
□ 删除 Activity 不删除历史会话和 AgentRun
□ 单个 Activity 失败不终止 Worker 或影响聊天
□ shutdown 先停止 Worker，再关闭 MCP 和 Provider
□ ACTIVITY_ENABLED=false 时 P0-P4 行为不变
□ 后端全量测试、前端 lint/build 和真实一次性任务验证通过
```

## 18. 明确的后续扩展门槛

只有出现对应真实需求或指标后再扩展：

| 触发条件 | 可考虑的扩展 |
|---|---|
| 单 Worker 经常造成明显延迟 | 独立 Worker + 数据库抢占 |
| 部署多个 API 实例 | PostgreSQL 锁或 Redis Queue |
| 用户确实需要复杂日历规则 | cron / timezone / DST 策略 |
| 出现稳定的外部事件来源 | Webhook / Event Trigger |
| 需要离线批准写操作 | 持久化 Approval，重新校验后执行 |
| 需要系统外提醒 | 浏览器通知、邮件或消息渠道 |
| 需要自然语言规划和任务拆解 | P6 Planner / Replanning |

P5 完成后的核心边界保持为：

```text
Activity（何时执行）
  -> Agent Runtime（如何完成）
  -> Skill / Tool / MCP（使用什么能力）
  -> Permission / ToolRun（是否安全、如何追踪）
```
