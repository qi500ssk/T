## 1. P0-P5 全项目逻辑审计结论

### 1.1 总体结论

当前项目逻辑可行，P0-P5 已形成一条闭合且方向正确的主链：

```text
Web / Activity
  -> FastAPI
  -> Agent Runtime
  -> Context Engine
  -> Model Gateway
  -> Skill / Tool / MCP
  -> Permission / ToolRun
  -> SQLite / Conversation / Message / AgentRun
```

基线验证结果：

```text
后端：73 passed, 1 skipped
前端：npm run lint 通过
前端：npm run build 通过
git diff --check 通过
```

跳过项是 Windows 环境无法创建符号链接的既有测试，不影响业务主链。当前实现适合单用户、单 API 进程、单 Activity Worker 的本地 Personal AI；不能宣称支持多用户隔离、多实例部署或大规模知识库。

### 1.2 已成立的架构边界

| 模块 | 审计结论 | P6 处理 |
|---|---|---|
| Model Gateway | LLM 与业务代码已解耦，stream / complete 足以支持规划 JSON 和流式执行 | 继续复用，不新增模型 SDK |
| Context Engine | Memory、RAG、Summary、Recent 有独立预算和总预算 | 规划步骤与观察结果必须纳入预算，不能绕过 Context |
| Memory | 提取、敏感信息过滤、去重、召回逻辑成立 | 计划和中间步骤不得被当作用户 Memory |
| RAG | 小规模 SQLite 下 Vector + BM25 + RRF 可用，引用由后端白名单控制 | P6 不重写检索；大规模性能另设门槛 |
| Tool / Approval | 白名单、参数校验、风险等级、超时、ToolRun 已闭环 | Planner 只能建议，不能扩大白名单或绕过审批 |
| MCP | stdio 发现、适配、故障隔离和关闭顺序成立 | 只读能力注册表展示 MCP 能力，不做热安装 |
| Activity | 计划持久化、单 Worker、重启恢复和后台 high 拒绝逻辑成立 | Activity 可选择 planned 模式，但仍由用户创建和调度 |
| Frontend | 只消费 REST/SSE，不决定工具和引用 | 只展示 Plan 状态；是否执行工具仍由后端决定 |

### 1.3 P6 开始前必须明确的风险

1. `core/agent.py` 已承担 Run 生命周期、上下文、模型循环、工具、审批、后处理；继续直接加入 Planner 会失控。P6 允许一次有实际用途的拆分，把“模型/工具执行循环”提取为扁平的 `core/executor.py`，Agent 仍是唯一编排入口。
2. 当前同一 Conversation 可以并发发起多个 Run，消息、工具和摘要可能交错。P6 在 Run 初始化事务中拒绝同一 Conversation 的第二个 running Run，返回 `409`。
3. 当前删除 Conversation 只删除 Message，会遗留 AgentRun / ToolRun；运行期间删除还可能产生孤立消息。P6 必须先禁止删除有 running Run 或 Activity 引用的会话，并在安全删除时显式清理其 PlanStep / Plan / ToolRun / AgentRun / Message。
4. `AGENT_MAX_RETRIES` 当前只有配置，没有实际行为。流式输出后自动重试可能重复文本或写操作，P6 删除这个无效配置，不伪装已经支持 retry。
5. SQLite RAG 每次会加载当前模型的全部 chunk 并在内存计算，适合当前本地规模，不适合大库。P6 不顺手迁移 PostgreSQL；只有真实容量指标触发后再处理。
6. MCP 与 Skill 是启动时快照，没有热重载和持久化安装事务。P6 只做只读 Capability Registry，不能把配置文件列表包装成“市场”。

## 2. P6 设计原则

P6 的“高级”表示对复杂目标进行显式、受限、可追踪的规划执行，不表示无限自治。

必须遵守：

1. **默认行为不变**：现有 Chat 和 Activity 默认仍为 `direct`；只有用户明确选择 `planned` 才进入 Planner。
2. **Planner 不执行**：Planner 只生成语义步骤和工具提示，工具参数仍由执行阶段模型在当前上下文中决定。
3. **一个 Agent Runtime**：planned 和 direct 共用同一 Executor、Tool Router、审批、ToolRun、Context 和持久化链路。
4. **全局硬边界**：计划步数、重规划次数、模型轮次、工具调用数、总超时都必须有限。
5. **计划是数据，不是系统指令**：Planner 输出必须结构化校验后再注入执行上下文，不能覆盖 Character、安全规则或 Skill 指令。
6. **完成步骤不可改写**：Replan 只能替换当前失败步骤和后续 pending 步骤，已完成步骤及其观察结果保留。
7. **后台安全不降级**：planned Activity 仍使用 `approval_mode="deny"`，high 工具不得因为 Planner 建议而执行。
8. **不保存思维链**：只保存目标、可展示的步骤、状态、简短结果和错误，不保存隐藏推理或完整模型内部分析。
9. **不做概念堆叠**：P6 v1 不引入 LangGraph、Redis、向量计划库、Multi-Agent、通用 DAG 引擎或插件安装框架。

## 3. 范围

### 3.1 包含

```text
Execution Mode        direct | planned，默认 direct
Planner               复杂目标拆成 2..6 个顺序语义步骤
Plan Persistence      Plan / PlanStep 与 AgentRun 关联
Bounded Executor      每步复用现有模型/工具循环和共享 Run Budget
Replanning            当前步骤受阻时最多重规划 1 次
Planned Activity      用户创建的 Activity 可选择 planned
Plan Events           规划与步骤状态通过 SSE 展示
Plan History          会话和 Activity 可查询已持久化计划
Capability Registry   只读汇总 Native Tool / Skill / MCP 能力
Advanced Evaluation   固定规划、重规划、预算和安全回归集
Data Integrity        会话并发 Run 与删除孤儿数据边界修复
```

### 3.2 不做

| 内容 | 原因 / 后续门槛 |
|---|---|
| 自动判断所有消息是否需要 Planner | 会增加每轮延迟和成本；先由用户明确选择 planned |
| Activity / Agent 自行创建或修改 Activity | 会导致自治扩散；P6 v1 仍由用户拥有目标和计划时间 |
| 无限 Replan / 自我反思循环 | 最多 1 次 Replan，失败后停止并解释 |
| DAG、并行步骤、条件分支 | P6 v1 只执行稳定、可观察的顺序步骤 |
| Planner 直接生成并执行工具参数 | 参数可能过期或越权；执行阶段重新结合当前上下文决策 |
| Multi-Agent / Agent-to-Agent delegation | 当前单 Agent 尚未证明需要角色拆分 |
| Skill Marketplace、在线安装、第三方代码下载 | 缺少签名、信任、依赖、权限和回滚模型 |
| Plugin 热启停、MCP 热重连 | 当前生命周期是启动快照；热更新需要独立事务边界 |
| Planner 自动批准 high 工具 | 交互 Run 仍需用户审批，后台 Run 仍立即拒绝 |
| 通用工作流产品、画布编辑器 | 超出 Personal AI 当前需求 |
| PostgreSQL / Redis / 分布式 Worker | 单用户单实例尚无容量证据 |
| LLM-as-a-Judge 在线评测 | 成本与不稳定性过高；先建立确定性离线指标 |

**P6 v1 完成边界**：用户明确选择规划模式后，系统可以生成可见计划，在一个 AgentRun 内逐步执行、必要时最多重规划一次，并留下完整状态；直接聊天和现有 Activity 行为不变；Planner 不能扩大权限或创建新的长期目标。

## 4. P6 最小架构

```text
POST /api/chat { execution_mode: "planned" }
  -> 初始化唯一 AgentRun
  -> build_context（Character / Memory / RAG / Summary / Recent / Skill）
  -> Planner.complete（严格 JSON）
  -> validate_plan
  -> 持久化 Plan + PlanStep
  -> 逐步调用共享 Executor
       -> LLM stream
       -> Tool / MCP
       -> Permission / Approval
       -> ToolRun
       -> Step observation summary
  -> blocked 且仍有额度？
       -> Replanner.complete
       -> supersede pending steps
       -> 执行新版本步骤
  -> 无工具 Final Synthesis
  -> Message + AgentRun + Plan 完成
```

模块职责：

```text
core/agent.py       Run 生命周期、direct/planned 编排、SSE、最终持久化
core/planner.py     Plan JSON 生成、解析、校验、Replan 和 Plan 数据操作
core/executor.py    共用的流式模型/工具/审批循环，不创建 AgentRun
core/registry.py    从已加载 Tool / Skill / MCP 构建只读能力快照
core/context.py     所有执行上下文与 token 预算
```

禁止：

```text
Planner -> execute_tool
Planner -> create Activity
PlanStep -> run_chat（会产生嵌套 AgentRun / Message / Memory）
Activity Worker -> 第二套 Planner / Executor
Frontend -> 直接标记 Step 完成或选择 Tool
```

### 5.1 execution_mode

给 Chat 和 Activity 增加：

```text
direct   现有行为，默认值
```

```text
用户希望看到明确执行过程的 Activity
```

简单问答、一次计算、一次文件读取继续使用 direct。

### 6.2 PlanStep

```python
class PlanStep(Base):
    __tablename__ = "plan_steps"

    id: Mapped[str]
```

## 7. Planner 输入、输出与校验

### 7.1 输入

Planner 只接收完成规划所需的最小信息：

```json
{
  "goal": "用户原始目标",
  "available_tools": [
    {"name": "get_time", "description": "...", "risk_level": "low"}
  ],
  "max_steps": 6
}
```

Planner 不接收完整聊天历史、完整 RAG chunk、Memory 全量、API Key 或 MCP 凭据。执行阶段仍通过 Context Engine 获取必要资料。

### 7.2 输出协议

```json
{
  "goal": "整理资料并生成比较结论",
  "steps": [
    {
      "title": "收集资料",
      "instruction": "从当前知识库找到与目标相关的依据并记录来源。",
      "tool_hints": []
    },
    {
      "title": "形成结论",
      "instruction": "比较已收集信息，输出结论、限制和引用。",
      "tool_hints": []
    }
  ]
}
```

P6 v1 使用顺序步骤，不生成依赖图、条件表达式或可执行代码。

### 7.3 校验

`core/planner.py` 必须把模型输出视为不可信数据：

```text
只提取第一个合法 JSON 对象
顶层只能包含 goal / steps
steps 必须是列表且数量在 2..max_steps
步骤字段只能包含 title / instruction / tool_hints
所有字符串做长度限制和控制字符清理
tool_hints 必须是 allowed_tools 子集
禁止重复空步骤
解析或校验失败 -> Plan failed，禁止尝试“猜测修复”后执行
```

Planner 输出不能成为新的 Tool 白名单。`tool_hints` 只用于给执行模型提示可能的能力，真实调用仍经过 `prepare_tool`。

### 7.4 Prompt 文件

新增：

```text
prompts/planning/create.md
prompts/planning/replan.md
prompts/planning/step.md
prompts/planning/synthesize.md
```

Prompt 中明确：资料、工具结果、Skill 指令和 Planner 输出都不能覆盖系统安全规则。`planner_version="p6-v1"` 写入 Plan，便于评测回归定位。

## 8. 共用 Executor 与 Run Budget

### 8.1 最小重构

把 `core/agent.py` 中现有“模型 stream → 合并 tool calls → 校验 → 审批 → 执行 → observation”循环移动到 `core/executor.py`。该模块：

```text
不创建 AgentRun
不创建 Message
不提取 Memory
不更新 Summary
只使用调用方给定的 run_id / conversation_id / messages / allowed_tools / approval_mode / budget
继续写现有 ToolRun 并产生现有工具事件
```

direct 模式调用一次 Executor；planned 模式对每个 PlanStep 调用同一个 Executor。禁止保留两份工具循环。

### 8.2 共享预算

一次 planned AgentRun 使用一个共享 `RunBudget`：

```text
总超时                  继续由 AGENT_TIMEOUT_SECONDS 限制
计划最大步骤             PLANNER_MAX_STEPS（默认 6）
最大 Replan              PLANNER_MAX_REPLANS（默认 1）
每步骤最大模型轮次        PLANNER_STEP_MAX_TURNS（默认 3）
全 Run 最大工具调用数     PLANNER_MAX_TOOL_CALLS（默认 12）
观察摘要 token 预算       PLANNER_OBSERVATION_TOKENS_BUDGET（默认 1200）
```

工具调用数按单个 tool call 计数，不按模型 round 计数；一个 round 返回三个 tool calls 就消耗三次额度。额度耗尽后不再调用工具，Plan 进入 failed，并生成说明性结果。

direct 模式继续受现有 `AGENT_MAX_STEPS` 控制，默认行为不改。P6 删除未使用的 `AGENT_MAX_RETRIES`，不增加隐式重试。

### 8.3 步骤上下文

每一步执行上下文由以下部分组成：

```text
原始 build_context 结果
当前 Plan goal
已完成步骤的 output_summary（受观察预算限制）
当前步骤 title / instruction
本 Run 实际 allowed_tools
```

不把所有中间工具结果和每一步完整模型输出无限累积到后续步骤。`output_summary` 是可展示事实摘要，不是隐藏推理。

### 8.4 步骤完成语义

```text
completed   模型正常结束，并产生非空步骤结果
blocked     本步需要的工具全部 rejected/failed/timeout，无法继续
failed      Provider、协议、预算或持久化错误导致步骤不能完成
cancelled   用户中止或应用 shutdown
```

单个 ToolRun failed 不必立即判定步骤失败；执行模型可以基于错误观察选择安全替代方案。只有本步结束时仍没有可用结果才是 blocked。

## 9. Replanning

### 9.1 触发条件

只在以下条件同时成立时触发：

```text
当前步骤 status == blocked
replan_count < PLANNER_MAX_REPLANS
RunBudget 仍有模型轮次和工具调用额度
AgentRun 未取消且总超时未到
```

模型 Provider 整体不可用、数据库错误、用户取消或总超时不触发 Replan，因为同一依赖下重试没有意义。

### 9.2 Replan 输入

```text
原始 goal
已完成步骤标题与 output_summary
当前 blocked 步骤及错误摘要
剩余 allowed_tools
剩余步骤数和工具预算
```

### 9.3 状态更新

Replan 成功时：

```text
旧版本当前 blocked 和后续 pending -> superseded
Plan.current_version += 1
Plan.replan_count += 1
插入新版本 pending 步骤
发出 plan.replanned
```

已 completed 步骤不删除、不改写、不重新执行。新计划仍必须通过与初始计划相同的校验，并且步骤数不能超过剩余额度。

Replan 失败或新计划仍受阻时，Plan 设为 failed。系统生成一条说明已完成内容、失败位置和未执行动作的助手消息；AgentRun 设为 failed，Activity 将本次执行视为失败。

## 10. Agent Runtime 集成

给 `run_chat` 增加一个兼容参数：

```python
async def run_chat(
    ...,
    activity_id: str | None = None,
    approval_mode: Literal["interactive", "deny"] = "interactive",
    execution_mode: Literal["direct", "planned"] = "direct",
) -> AsyncIterator[AgentEvent]:
```

### 10.1 direct

```text
初始化 AgentRun(execution_mode=direct)
build_context
调用共享 Executor
保存 Message / Token Usage
Memory / Summary 后处理
```

事件、审批和回复行为必须与 P5 完全兼容。

### 10.2 planned

```text
初始化 AgentRun(execution_mode=planned)
build_context
Planner -> Plan/Steps
逐步 Executor
必要时 Replan
无工具 Final Synthesis
保存一个最终 assistant Message
跳过对中间计划文本的 Memory 提取
仍只对原始用户输入和最终回复执行既有 Memory 提取
更新 Summary
```

Activity Run 继续跳过 Memory 提取，与 P5 一致。

### 10.3 失败与消息

规划失败或步骤最终受阻时，仍要保存一条对用户有用的 assistant 说明，但 AgentRun / Plan 状态为 failed，并发送 `run.failed`。不能为了显示回复而把未完成目标标记为 completed。

## 11. Agent Event Protocol

保留既有事件，新增事件只能增量解析：

```text
plan.created
plan.step.started
plan.step.completed
plan.step.blocked
plan.replanned
plan.completed
plan.failed
```

示例：

```json
{
  "event": "plan.step.completed",
  "data": {
    "plan_id": "...",
    "step_id": "...",
    "version": 1,
    "position": 1,
    "title": "收集资料",
    "status": "completed",
    "output_summary": "找到 3 条相关资料"
  }
}
```

约束：

```text
事件不包含隐藏推理、完整 Prompt、凭据或完整 Tool Result
message.delta 只用于最终面向用户的回复；步骤状态使用 plan.*
tool.* / approval.* 事件结构保持不变
run.started / run.completed / run.failed 保持兼容
```

## 12. Planned Activity

Activity 创建请求增加可选字段：

```json
{
  "execution_mode": "planned"
}
```

历史 Activity 迁移后均为 direct。Worker 仍只调用 `run_chat`，传入 Activity 保存的 execution_mode，不创建第二套 Planner。

后台 planned 规则：

| 风险 | 行为 |
|---|---|
| low | 在白名单和预算内执行 |
| medium | 沿用现有工具规则执行 |
| high | rejected，不创建审批 waiter；允许 Replan 寻找安全替代路径 |

Planned Activity 仍不能：

```text
创建新 Activity
修改自己的 schedule / prompt / execution_mode
启用 Plugin 或 MCP Server
绕过 high 拒绝
无限续写目标
```

这是一种“用户拥有目标、Agent 受限规划执行”的 bounded autonomy，不是 Autonomous Activity 自我繁殖。

## 13. Capability Registry（只读）

P6 v1 将架构中的 Plugin Registry 收敛为只读 Capability Registry，解决“Planner 到底有哪些能力”与“用户能否查看当前能力”的问题。

新增 `core/registry.py`，从应用启动后真实加载的对象构建快照：

```text
Native Tool
MCP Tool（含 server 来源）
Skill（含 required_tools）
MCP Server（connected / unavailable）
```

统一字段：

```json
{
  "kind": "tool",
  "name": "mcp_demo_echo",
  "description": "...",
  "source": "mcp:demo",
  "risk_level": "low",
  "required_tools": [],
  "enabled": true,
  "available": true
}
```

注册表不新增数据库表，不成为第二个 Tool Registry；Planner 的 available_tools 必须来自当前请求的 `allowed_tools` 与这份快照的交集。

P6 v1 不提供安装、卸载、在线搜索、版本升级、凭据编辑或运行时启停。真正 Marketplace 必须先定义签名、来源信任、权限清单、依赖隔离、安装事务、回滚和审计，不能直接下载第三方代码。

## 17. 生命周期与取消

启动顺序在 P5 基础上保持：

```text
init_db（P6 迁移）
Provider / Embedding
MCP 连接并注册 Tool
Skill 加载
构建 Capability Registry 快照
Activity 恢复和 Worker
接受请求
```

Planner 不创建全局后台任务，不需要单独 close。

取消语义：

```text
用户中止 SSE / 应用 shutdown
  -> 当前 Tool / Provider 调用取消
  -> running PlanStep = cancelled
  -> remaining pending = cancelled
  -> Plan = cancelled
  -> AgentRun = cancelled
  -> 清理 approval waiter
```

Activity Worker 被取消时仍保留 P5 的 running Activity 恢复语义；下次启动会重新排队整个 Run，不从中间 PlanStep 恢复。P6 v1 不承诺 step-level exactly-once。

## 18. 安全边界

### 18.1 Prompt Injection

```text
Planner 输出、PlanStep、RAG 文本、Tool Result、MCP Result 均标记为不可信数据
Character / System Safety / Permission 的优先级始终更高
Plan 指令不能要求忽略系统规则、读取凭据或扩大工具白名单
```

计划文本注入 System 时必须使用明确分隔和长度限制。不要把模型生成的 Plan 直接拼成新的最高优先级 System Prompt。

### 18.2 权限

```text
tool_hints ⊆ allowed_tools
真实工具调用再次 prepare_tool
风险等级只来自 Tool Registry
interactive high -> 每次按准确 args_summary 审批
background high -> rejected
Replan 不会重置已拒绝工具的权限状态
```

### 18.3 数据与日志

Plan / PlanStep 不保存完整工具结果、完整 Prompt、模型隐藏推理、MCP stderr 或 Secret。结构化日志只记录 run_id、plan_id、step_id、状态、耗时、工具名和截断错误。

### 18.4 自治限制

Planner 没有以下能力：

```text
调用 Activity CRUD
编辑 Skill / MCP 配置
安装 Plugin
修改 Character / Prompt
修改自身预算
生成子 Agent
在 Run 结束后继续运行
```

## 19. 错误与恢复

```text
Planner JSON 无效          Plan failed；保存说明，不执行猜测计划
计划校验失败               Plan failed；记录截断错误
步骤 Tool failed           交回 Executor；可安全替代，否则 blocked
用户拒绝 high              当前步骤可 Replan；不可偷偷重试原操作
后台 high                  rejected；可 Replan 为只读替代
预算耗尽                   Plan failed；停止工具调用并解释
Provider 故障              AgentRun / Plan failed，不 Replan
数据库故障                 当前 Run failed；不继续执行外部动作
用户取消                   Plan / Step / AgentRun cancelled
应用重启                   P5 重跑整个 Activity；不恢复半个 Plan
Capability 不可用          规划校验或步骤执行明确失败
```

Final Synthesis 只允许模型生成文本，不提供 tools，避免完成计划后又启动未记录的动作。


## 24. P6 v1 之后的扩展门槛

| 真实触发条件 | 可考虑扩展 |
|---|---|
| 大量用户经常手动选择 planned | 增加经过评测的 auto planning gate |
| 顺序步骤无法表达稳定业务 | 引入有限条件分支，再评估 DAG |
| 单 Agent 的工具上下文明显不足 | 评估角色化子 Agent，但必须共享预算与权限 |
| 用户明确要求 Agent 自建长期目标 | 设计持久化 Goal、配额、确认和撤销，再开放 Autonomous Activity |
| 有可信第三方 Skill 分发需求 | 设计签名、来源信任、权限 manifest、依赖隔离与回滚 |
| 需要运行时启停 MCP / Skill | 设计原子 Registry 更新和连接生命周期，不直接改全局 TOOLS |
| planned Activity 因单 Worker 延迟 | PostgreSQL 抢占或独立 Worker，而不是先上 Redis |
| 固定评测无法判断真实质量 | 引入版本化人工标注或离线 Judge，保留确定性安全指标 |

P6 v1 完成后的稳定边界：

```text
用户拥有 Goal 与 Activity
  -> Planner 生成受限 Plan
  -> Agent Runtime 编排
  -> Executor 使用现有 Skill / Tool / MCP
  -> Permission / Budget 决定能否执行
  -> Plan / ToolRun / AgentRun 提供可观察历史
```

系统可以更有条理地完成复杂目标，但目标来源、长期调度和高风险授权仍掌握在用户手中。
