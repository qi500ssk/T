# Agent 数据库选型与切换指南

更新日期：2026-09-11。面向本项目的开发与后续产品规划。

本文回答四个问题：Agent 常用哪些数据库、它们有什么区别、什么时候选什么、已有项目能否切换及如何切换。产品能力参考官方文档；场景建议是结合本项目作出的工程判断，不是性能排名。

**先记住：Agent 没有一种必须使用的数据库。账号和聊天记录、语义检索、缓存、文件与关系查询，解决的是不同问题，可以由一个数据库承担，也可以按需要组合。大部分数据可以迁移，但功能、索引和查询代码不一定能直接照搬。**

## 1. 先看 Agent 要保存什么

| 数据或需求 | 例子 | 通常放在哪里 |
| --- | --- | --- |
| 业务记录 | 账号、会话、消息、项目、权限、任务状态、审批记录 | SQLite、PostgreSQL、MySQL；文档模型合适时也可用 MongoDB |
| 长期记忆原文 | 用户偏好、项目事实、记忆来源、更新时间、是否失效 | 主业务库；需要语义查找时再建立向量索引 |
| 知识库检索 | 文档切片、向量、来源页码、所属项目 | 主库加向量能力，或专门的向量库 |
| 临时状态 | 限流计数、短期缓存、跨进程共享状态 | 进程内内存；需要跨进程时考虑 Redis |
| 全文检索 | 搜索错误码、函数名、产品型号、精确短语 | 数据库全文索引，或 Elasticsearch 等搜索系统 |
| 多步关系查询 | 某项目由谁负责、与哪些合同和公司有关 | 关系简单时用主库；复杂多跳关系可考虑 Neo4j |
| 原始文件 | PDF、图片、音频、生成的 Word | 本地文件系统或对象存储；主库保存文件 ID 和元数据 |
| 分析统计 | 大批日志聚合、CSV/Parquet 分析、使用情况报告 | DuckDB 等分析数据库 |

这里的“主业务库”是业务事实的权威来源。例如文档是否被删除、谁能查看它，应有明确的权威记录；不能只凭一个可能尚未同步的向量索引判断。

“长期记忆”也不等于“向量数据库”。保存、筛选、更新、遗忘和引用记忆是应用逻辑；向量检索只是找出相关记忆的一种方式。

## 2. 保存账号、聊天和任务：主业务数据库

| 方案 | 核心区别 | 适合的 Agent 场景 | 主要取舍 |
| --- | --- | --- | --- |
| SQLite | 嵌入应用，直接读写本地数据库文件，不需要单独数据库服务 | 可下载的个人 Agent、本地工具、轻量单机服务 | 部署简单；同一数据库文件同时只能有一个写事务 |
| PostgreSQL | 独立数据库服务，支持事务、关联查询、丰富类型与扩展 | 多人使用的网页 Agent、较复杂业务、希望把业务与向量放在一起 | 需要管理连接、备份、升级和服务可用性 |
| MySQL，通常使用 InnoDB | 独立关系型数据库服务，成熟的事务业务生态 | 团队已有 MySQL 的网站、客服 Agent、业务系统集成 | 适合沿用既有技术；向量能力需按实际版本和部署产品核实 |
| MongoDB | 以 BSON 文档组织数据，适合嵌套、结构变化较多的对象 | 工具结果或业务对象天然是文档，团队熟悉 MongoDB | 要设计字段规则、索引和一致性；从 SQL 表迁入通常需重写查询 |

SQLite 可以被多个连接使用，也可以支持网站，并不是“只能一个用户”。真正应关注的是写入竞争、事务长度、部署结构和可用性要求；其官方建议在大量客户端通过网络直接访问同一个数据库时考虑客户端/服务端数据库。[SQLite 适用场景](https://www.sqlite.org/whentouse.html)

PostgreSQL 的类型与扩展生态、MySQL InnoDB 的事务能力、MongoDB 的文档模型是不同的技术特点，并不构成通用的优劣排名。[PostgreSQL 数据类型](https://www.postgresql.org/docs/current/datatype.html)、[MySQL InnoDB 多版本机制](https://dev.mysql.com/doc/refman/8.0/en/innodb-multi-versioning.html)、[MongoDB 文档模型](https://www.mongodb.com/docs/manual/core/document/)

**对本项目的判断：**现在做每个人下载安装的本地软件，SQLite 符合免部署数据库、数据保存在自己电脑上的方向。以后单独做多人网页端，可以优先评估 PostgreSQL；如果那时的团队和系统已经使用 MySQL，沿用 MySQL 也合理。

补充：Supabase 是基于 PostgreSQL 的平台，包含数据库及其他服务，不能把它当成与 PostgreSQL 完全不同的数据库引擎。迁出其数据库与迁出认证、文件存储等平台服务是不同工作。[Supabase 数据库说明](https://supabase.com/docs/guides/database/overview)

## 3. 根据含义找资料：向量存储与检索

例如用户问“怎样找回登录密码”，即使资料中写的是“使用恢复码重置凭据”，向量检索也可能找到相关内容。它通常需要先用 embedding 模型把文本转成数字向量。

| 方案 | 主要特点 | 什么时候考虑 |
| --- | --- | --- |
| 本项目的 SQLite JSON 向量 | 向量与业务数据同库，由自定义函数扫描计算相似度 | 当前个人资料库，优先保证简单、可打包；检索延迟尚可接受 |
| PostgreSQL + pgvector | 在 PostgreSQL 中增加向量类型与检索能力，支持精确检索及 HNSW、IVFFlat 索引 | 已用 PostgreSQL，希望减少额外服务，并结合业务过滤条件检索 |
| Chroma | 提供本地持久化客户端，也有服务端和云端连接方式 | 快速构建 RAG；评估其本地模式与安装包、备份需求是否匹配 |
| LanceDB | 提供嵌入式、多模态检索能力，也有其他部署产品 | 本地资料、多模态数据，希望评估嵌入式检索方案 |
| Qdrant | 专门的向量检索系统，提供向量与元数据过滤等能力 | 向量检索需要独立扩展，或者复杂过滤与检索成为重点 |
| Milvus | 提供 Lite、Standalone、Distributed 等部署方式 | 从本地验证到独立向量服务、分布式部署有明确需求 |
| Weaviate | 提供关键词、向量和混合检索 | 希望在同一检索系统中组合关键词与语义结果 |
| Pinecone | 通过托管服务使用向量等检索能力 | 接受数据进入所选云服务，希望减少自运维工作 |
| FAISS | 向量相似度搜索库，主要提供索引与搜索算法 | 希望自己控制索引与检索流程，愿意补充元数据、持久化和服务管理 |

产品能力来源：[pgvector](https://github.com/pgvector/pgvector)、[Chroma 客户端](https://docs.trychroma.com/docs/run-chroma/clients)、[LanceDB](https://github.com/lancedb/lancedb)、[Qdrant 过滤](https://qdrant.tech/documentation/search/filtering/)、[Milvus 部署方式](https://milvus.io/docs/install-overview.md)、[Weaviate 检索](https://docs.weaviate.io/weaviate/concepts/search)、[Pinecone](https://docs.pinecone.io/guides/get-started/overview)、[FAISS](https://faiss.ai/)。具体能力、平台支持与许可要以实际安装版本为准。

这些方案不能统一理解为“把 SQLite 整个替换掉”。例如采用 Qdrant 后，可以继续让 SQLite 保存账号、消息和任务，只把向量检索交给 Qdrant。FAISS 则是检索库，不能直接承担整个账号与任务数据库的职责。

不要按“超过一万条就必须换库”这样的固定数字决策。向量维度、过滤范围、硬件、检索并发、索引参数以及可接受的准确率都会影响结果。先测实际查询的耗时和召回质量，再决定是否增加索引或更换检索系统。

本项目目前没有使用 SQLite 的专门向量索引扩展，不能把“已经保存向量”理解为“已经具备大规模向量索引”。

## 4. 其他常见数据库解决什么问题

| 方案或类型 | 擅长什么 | Agent 中的使用方式 | 是否应直接替换主库 |
| --- | --- | --- | --- |
| Redis | 低延迟数据访问、过期机制、计数器、Streams 等 | 缓存、限流、共享临时状态；需要时结合可靠消费机制处理事件 | 通常作为补充；若承担长期权威数据，需专门设计持久化和恢复 |
| Elasticsearch 等搜索系统 | 全文搜索、过滤、搜索分析，也可支持向量检索 | 企业知识库、日志和代码搜索，需要关键词与语义结合 | 通常保留业务主库，把搜索索引作为可重建副本 |
| Neo4j | 显式表达节点与边，沿关系查询 | 知识图谱、复杂多跳关系、GraphRAG | 通常增加图模型；业务关系简单时未必需要 |
| DuckDB | 嵌入式分析查询、批量扫描和聚合 | 分析 Agent 处理数据集、日志统计、报告生成 | 通常用于分析侧，不作为本项目账号与任务状态的首选 |
| 本地文件系统、对象存储 | 保存文件内容 | PDF、图片、模型资源、生成文件 | 与数据库配合使用，本身不提供完整的关系型业务能力 |

能力参考：[Redis 数据类型](https://redis.io/docs/latest/develop/data-types/)、[Elasticsearch 向量检索](https://www.elastic.co/docs/solutions/search/vector/dense-vector)、[Neo4j GenAI](https://neo4j.com/docs/genai/)、[DuckDB 定位](https://duckdb.org/)。以上使用方式是本指南的架构建议。

Redis 不只是缓存，也不意味着断电必然丢掉所有数据；不过不能在不了解持久化配置和故障恢复的情况下，把缓存当成唯一的数据存档。图数据库同样不会自动把所有聊天内容变成正确知识图谱，仍需要实体提取、消歧、来源记录和更新逻辑。

## 5. 什么时候选什么：按产品形态决定

| 实际需求 | 可以先评估的组合 | 何时增加组件 |
| --- | --- | --- |
| 可下载、个人本地 Agent | SQLite + 本地文件 | 检索实际变慢后，评估本地向量索引或嵌入式检索库 |
| 小型自用网页服务 | SQLite 或 PostgreSQL + 文件存储 | 出现写锁等待、多个后端实例或服务可用性要求后重新评估 |
| 多用户网页 Agent | PostgreSQL 或 MySQL + 文件/对象存储 | 根据共享状态、搜索和向量负载，分别评估 Redis 与检索服务 |
| 已有 MySQL 的企业系统 | 沿用 MySQL，按需增加向量检索 | 不必为了“使用 Agent”先搬迁所有业务数据 |
| PostgreSQL 上增加知识库 | PostgreSQL + pgvector | 独立伸缩、检索负载或功能需求足以抵消额外运维成本时拆出检索库 |
| 文档对象变化多且已有 MongoDB | MongoDB；按部署能力选择检索方式 | 根据实际查询及一致性要求调整模型 |
| 强调本地离线知识库 | SQLite + 本地 embedding + 本地检索 + 本地文件 | 逐项验证模型、依赖和所有检索步骤能否离线运行 |
| 大量知识库搜索 | 业务主库 + 专门向量/搜索系统 | 先用真实资料、真实权限过滤和查询做评测 |
| 复杂关系推理 | 主库 + Neo4j 等图存储 | 当关系查询确实成为核心能力，而非仅需要简单关联 |
| Agent 分析大量表格与日志 | 主库 + DuckDB 等分析引擎 | 分析负载与在线业务负载需要不同优化时 |

这些是候选组合，不要求把所有组件都装上。每增加一个服务，都增加部署、备份、监控和数据一致性的工作。

“多人使用”也不等于必须每人建一套数据库。网页端可以使用共享数据库并严格隔离用户数据，也可以按租户分库；两者都需要应用正确实施权限。你当前的桌面产品方向则是每个安装用户在本机保存自己的数据。

## 6. 能不能切换？先确定切换的对象

| 切换方式 | 是否可行 | 主要改动 |
| --- | --- | --- |
| 同种引擎换服务器，例如 PostgreSQL A → B | 通常可行 | 备份恢复、版本与扩展兼容、账号权限、连接配置 |
| SQLite → PostgreSQL / MySQL | 通常可行 | 表结构、类型、SQL 方言、锁与事务、自增/序列、数据导入和验证 |
| PostgreSQL ↔ MySQL | 通常可行，但不是直接恢复对方备份 | 专有类型、SQL、索引、函数、排序规则、事务及迁移代码 |
| 关系数据库 → MongoDB | 可以迁移数据 | 重设计文档模型、关联关系与查询，通常不是简单更换驱动 |
| Chroma / Qdrant / pgvector 等向量方案互换 | 通常可迁移可导出的向量和元数据 | ID、向量维度、距离计算、过滤语义、删除与权限规则、重建索引 |
| 本地向量库 → 云端向量服务 | 技术上通常可行 | 除检索适配外，还要确定哪些文本、向量与元数据允许上传 |
| 主业务库 → 只使用向量库 | 通常不是对等替换 | 必须重新解决事务、唯一性、账号、审批和业务状态管理 |
| SQLite 主库 + 新增向量库 | 可行，属于增加组件 | 保留主库，增加可重建索引及其同步逻辑 |

**是否能切换，取决于源数据能否完整导出、目标能否表达原有业务语义，以及是否愿意完成代码适配。**如果源产品只允许使用封闭索引、拿不到原文或向量，迁移可能需要重新从原始资料构建，甚至受导出能力限制。

修改 `DATABASE_URL` 只会改变连接目标，不会自动搬运旧数据，也不会把 PostgreSQL 专用语法转换成 SQLite。SQLAlchemy 能统一部分访问方式，但它不会消除全部数据库差异。[SQLAlchemy 引擎与连接配置](https://docs.sqlalchemy.org/en/20/core/engines.html)

同引擎备份工具也不是跨引擎转换器。`pg_dump` / `pg_restore` 面向 PostgreSQL，`mysqldump` 的 SQL 输出面向 MySQL；不能默认把其中一个的输出直接交给另一个执行。[PostgreSQL pg_dump](https://www.postgresql.org/docs/16/app-pgdump.html)、[MySQL mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

## 7. 业务数据库怎样迁移

下面是适合当前小型项目的“暂停写入后迁移”流程。大系统的持续同步迁移，需要另外设计变更捕获、重试、去重、删除同步与切换边界。

1. **盘点数据与行为。**列出表、字段、索引、外键、账号摘要、任务状态、时间格式，以及数据库外的文件与配置。
2. **备份并验证能恢复。**保留源库、对应代码版本和配置；不能只备份一个连接地址。
3. **暂停旧系统写入。**先结束或明确处理运行中的 Agent 任务，避免只迁走旧快照而漏掉新消息。
4. **创建目标表结构。**将数据类型、默认值、唯一规则和索引转换到目标数据库，并建立正确的 schema 版本。
5. **导入记录。**保留 ID 与关联；按依赖顺序导入或使用目标库支持的约束处理；不要因字段不兼容而静默丢弃关键值。
6. **验证数据和业务。**核对各表数量、关键字段、外键、时间、密码验证、聊天历史、记忆召回与文档引用；仅行数相同不代表内容完全正确。
7. **切换应用代码与配置。**使用已适配目标数据库的版本，重新启动并做登录、聊天、任务和文件读取检查。
8. **保留回退条件。**观察稳定后再处理旧库；不要立刻删除源数据。

尤其要检查：

| 容易忽略的差异 | 可能造成什么问题 |
| --- | --- |
| 时间与时区 | 登录提前失效、排序变化、任务时间偏移 |
| 布尔值、JSON、数组和空值 | `NULL`、空字符串、JSON `null` 被混淆 |
| 字符串长度、大小写和排序规则 | 原来不同的用户名被目标库视作重复，或者约束变松 |
| 主键、自增值、序列 | 旧记录导入成功，但新增记录撞上已有 ID |
| 部分唯一索引、数据库函数 | “同一会话只允许一个运行任务”等规则失效 |
| 事务与锁 | 同一个恢复码被并发使用，或密码修改只保存了一半 |
| 金额等精确数值 | 转成浮点后失去原精度；应设计明确的精确存储方式 |
| 外部文件路径 | 文档记录在新库里，原 PDF 或图片却无法读取 |

SQLite 的类型亲和性、布尔值和日期表示与常见服务端数据库不同，例如声明 `VARCHAR(80)` 本身并不会像某些数据库那样限制长度，需要在应用或约束中落实规则。[SQLite 数据类型](https://www.sqlite.org/datatype3.html)

回退也需要区分时间点：切换后尚未产生新数据，回到旧代码与旧库相对简单；如果新库已产生聊天、密码修改等记录，直接回退会丢失这些变化，需要先处理增量数据。

## 8. 向量数据库怎样迁移

一个可迁移的知识切片，至少应能找回：`chunk_id`、原文、`document_id`、来源位置、所属用户/项目、embedding 模型和版本、向量维度、向量值、更新时间与删除状态。

推荐流程是：导出向量与元数据 → 在目标创建集合和过滤索引 → 批量导入 → 重建向量索引 → 用固定问题集对比 → 切换读写 → 保留旧索引至验证结束。

| 发生了什么变化 | 要不要重新计算 embedding |
| --- | --- |
| 只更换数据库，原文、切片、模型及预处理不变，向量可兼容导出 | 通常可以复用向量；仍需重建目标索引 |
| 更换 embedding 模型或模型版本 | 通常需要重算受影响内容，查询也必须使用匹配模型 |
| 模型不同但输出维度相同 | 不能因此混用；维度相同不代表向量空间相同 |
| 切片方式或原文变化 | 重算发生变化的切片，并清理失效索引 |
| 源库只能导出原文，无法导出向量 | 需重新生成向量；先确认来源内容完整 |
| 距离函数或归一化方式变化 | 先验证数学与模型兼容性，必要时转换或重算 |

HNSW 等索引文件通常不是各产品之间的通用交换格式。应优先保留可导出的原始数据、原始向量与元数据，而不只保存某个产品的内部索引。

迁移后不仅测“能搜到结果”，还要测：正确资料能否进入前几名、引用能否定位原文、不同项目是否串数据、删除是否生效、耗时和资源占用是否达标。不同产品对“相似度”和“距离”的分数方向与范围可能不同，原阈值不能直接照搬。

如果将主库与向量库拆开，本地小项目可以先采取暂停写入后重建索引的方式；持续运行的系统则需要可靠的同步队列或 outbox、幂等写入、删除同步与版本核对。单纯连续调用两次写入 API，不会自动获得跨数据库事务。

## 9. 本项目这次 PostgreSQL → SQLite 的实际例子

本节描述已经完成的实现；前文其他数据库是候选方案，并未全部接入项目。

| 改动 | 实际做法 |
| --- | --- |
| 连接与依赖 | 正常运行改为本地 SQLite，移除常规运行所需的 PostgreSQL 驱动和 pgvector；旧库导入驱动放在可选依赖组 |
| 表结构迁移 | 新增 `migrations/sqlite_versions/`；保留旧 PostgreSQL 迁移历史，SQLite 不运行旧历史 |
| 时间 | `UTCDateTime` 写入前统一到 UTC，读取时补回 UTC 时区信息 |
| 向量 | 由 pgvector 类型改成 JSON 浮点数组；校验维度和有限数值，使用自定义余弦距离函数 |
| 索引与约束 | 改用 SQLite 的部分索引条件，连接启用外键检查 |
| 并发写入 | 开启 WAL 与写锁等待；账号修改用 `BEGIN IMMEDIATE` 在校验与写入期间保持事务保护 |
| 恢复码 | 用条件更新保证只能消费一次；账号、密码、恢复码、会话修改由调用方统一提交或回滚 |
| 原数据 | 导入脚本对 PostgreSQL 使用只读一致快照，写入全新 SQLite 文件并校验记录数、外键和完整性 |
| 登录状态 | 保留账号与密码摘要，跳过旧登录会话，迁移后重新登录 |
| 备份与测试 | 新增 SQLite 在线备份工具；测试使用独立临时数据库 |

WAL 允许读写更好地并行，但没有取消 SQLite 每个数据库文件只能有一个写事务的限制；备份也必须包含已提交到 WAL 的数据，不能随意只拷贝运行中的主文件。[SQLite WAL](https://www.sqlite.org/wal.html)

截至此次迁移检查，导入了 9 个会话、92 条消息、3 份文档，以及记忆、项目和执行记录；源 PostgreSQL 未修改。当时原账号的恢复码记录为 0，迁移后仍为 0，需要用户在账号设置里生成。代码验证结果为 259 项测试通过、1 项跳过，前端构建通过；这不等于已经完成所有规模的性能测试。

## 10. 对当前产品的建议与可迁移性约定

当前继续使用 **SQLite + 本地文件存储**，先把登录、聊天、任务恢复、备份与安装更新做稳定。保留原文、切片、稳定 ID 和模型版本信息；当真实检索负载变大时，优先评估是否只升级检索部分。

未来独立开发网页端时，再根据并发写入、后台部署和运维能力选择 PostgreSQL 或 MySQL；是否加 Redis、向量库、搜索或图数据库，由具体功能和测试结果决定。这里只记录方向，不提前给本项目引入所有数据库适配层。

为降低以后切换成本，持续遵守以下约定：

1. 主业务数据、派生索引和原始文件分别明确谁是权威来源，派生索引应能重建。
2. 使用稳定的业务 ID、明确的时间与空值约定；用户和项目范围必须随数据一起迁移。
3. 保留原文、引用位置、embedding 模型与版本，允许导出实际需要的向量和元数据。
4. 数据库专用能力集中在明确模块；有第二种实现的实际需求时，再提取接口。
5. 应用升级新增表或字段时编写 schema 迁移，避免让用户通过删库获得新版本。
6. 验证备份能够恢复；切换时验证功能、权限、检索质量与性能，而不只是“连接成功”。

新安装默认把数据库放在当前系统用户的数据目录。不同电脑或不同系统用户正常情况下拥有各自的数据；同一系统用户打开多个软件副本，若未指定不同目录，仍会指向同一份数据库。发行包必须排除开发者数据库、`.env`、备份和个人文件。

数据库保存在本机不等于所有内容都不离开电脑：调用云端模型、云端 embedding 或云端检索时，必要内容仍会发送到所选服务。离线能力必须同时核对模型、存储、检索和工具调用。
