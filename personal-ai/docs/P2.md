## 一、交付结论

P2 已完成“上传 → 安全存储 → 解析 → 分块 → Embedding → 混合检索 → Context 注入 → 流式引用 → 前端展示 → 离线评测”的完整闭环。

本阶段遵守“小规模个人知识库先验证闭环”的原则，使用 SQLite JSON 保存向量并在应用层计算相似度，没有提前引入 PostgreSQL、pgvector、Worker、OCR、Reranker 或 Tool Calling。P0/P1 的聊天、记忆、摘要和 SSE 基础事件保持兼容。

## 四、数据模型

### 4.1 Document

保存用户、原始文件名、安全存储文件名、MIME、文件类型、字节数、状态、错误、chunk 数、SHA-256、Embedding 模型/维度和时间。

状态流转：

```text
pending → indexing → indexed
                   ├→ needs_ocr
                   └→ failed
```

数据库强制 `UNIQUE(user_id, content_hash)`，相同用户上传相同字节内容返回 HTTP 409 和已有 document_id。

### 4.2 DocumentChunk

保存 document_id、chunk_index、section、content、页码、字符偏移和 JSON 向量。数据库强制 `UNIQUE(document_id, chunk_index)`，并通过外键关联 Document。

### 4.3 Message.citations

助手消息新增 JSON citations。它只保存本轮真正进入模型 Context 的 source 元数据；页面刷新后直接从消息 API 重新渲染，不依赖已经结束的 SSE 流。

### 4.4 兼容迁移

`init_db()` 继续使用阶段性 `create_all + 幂等迁移`。已有 P1 SQLite 缺少 `messages.citations` 时执行固定 `ALTER TABLE`；新表由 SQLAlchemy 创建。P0/P1 的会话、消息、摘要和记忆不删除、不重建。

## 五、完整运行逻辑

### 5.1 上传与索引

```text
POST /api/files
  ↓ 最多读取 FILE_MAX_BYTES + 1
扩展名 + MIME + 文件头/文本编码联合校验
  ↓ 校验失败：413/415，不创建 Document
SHA-256 查询重复内容
  ↓ 重复：409 + 已有 document_id
UUID 文件名安全落盘
  ↓
创建 Document(pending)
  ↓ anyio 线程池
Document(indexing)
  ↓
Parser → ParsedBlock[]
  ↓ needs_ocr / 页数、字符、解压上限检查
完整句分块 + embedding tokenizer 上限
  ↓
按 EMBEDDING_BATCH_SIZE 批量生成归一化向量
  ↓
同一事务保存 chunks，Document(indexed)
```

解析、资源上限或模型异常不会删除记录，而是保存 `failed + 可读错误`，便于 UI 展示和用户删除。扫描 PDF 保存为 `needs_ocr`。

### 5.2 混合检索

```text
用户问题
  ├─ BGE query instruction + query → normalized vector → Vector top-12
  └─ jieba(query) → BM25 top-12
                     ↓
          RRF: Σ 1 / (60 + rank)
                     ↓
仅 vector 独中候选执行 cosine 最低值过滤
BM25 独中或双路命中保留
                     ↓
                 final top-5
```

不对 RRF 总分设置绝对阈值，避免用错误尺度误杀全部结果。

### 5.3 Context 与引用

上下文装配顺序：

```text
预留 System + 当前问题
  → Memory（默认 600 tokens）
  → RAG（默认 800 tokens，只装完整 source）
  → Summary（默认 800 tokens）
  → Recent Messages（使用剩余预算）
  → CONTEXT_MAX_TOKENS 硬上限复核
```

RAG source 使用 XML 转义后的文件名、章节和正文：

```xml
<source citation_id="c1" file="晨星项目说明.md" section="故障处理">...</source>
```

`prompts/rag/context.md` 明确资料仅为证据，资料中的命令和角色设定不得作为系统指令。一个 source 只有在完整放入 RAG 分区和总预算后，才会同时进入：

1. 模型 Context；
2. `rag.retrieved.sources`；
3. 助手消息 `citations`。

因此前端引用白名单与模型实际看到的证据一致。

### 5.4 聊天 SSE

```text
run.started
rag.retrieved       # 有实际 source 时才发送
message.delta       # 逐段文本
message.completed
run.completed
```

无资料或未命中时不发送 `rag.retrieved`，原 P0/P1 客户端仍可正常工作。模型回答中出现不在白名单的 `[c99]` 时，后端记录警告；前端不会创建对应卡片，只把它当普通文本显示。

### 5.5 Knowledge UI

- Sidebar 使用“对话 / 记忆 / 知识库”分段导航；
- 上传时限制浏览器选择 PDF/DOCX/TXT/MD，真正安全校验仍由后端执行；
- 文档列表展示大小、状态、chunk 数和错误；
- 详情展示前 20 个 chunk、章节和页码；
- 检索预览显示最终排名和证据片段；
- PDF 原文链接附带 `#page=N`；TXT/MD 浏览器打开；DOCX 下载；
- 删除需要确认，数据库事务成功后再删除磁盘原文件。

## 十、代码规则执行情况

- 没有把 Embedding 塞进聊天 Gateway；两者职责独立；
- 没有绕过 Context Engine 直接把历史或文档传给 LLM；

- 数据库模型仍集中在 `infrastructure/database.py`；

- 没有新增无用途的 Factory、Manager、Repository 或多层 BaseClass；
- 文件删除显式处理 chunk 和 document，不依赖 SQLite cascade 作为唯一保障；
- 没有改动或弱化 P1 的数据库唯一约束和敏感信息过滤。

## 十一、当前限制

1. SQLite 会全量读取当前用户的 chunk 向量并在应用层计算相似度，适合个人、小规模知识库，不适合百万级数据。
2. 上传请求会等待索引完成；线程池避免阻塞事件循环，但单次模型 encode 无法被强制中断，超时是阶段检查式。
3. PDF 扫描件只标记 `needs_ocr`，本阶段不做 OCR。
4. DOCX 引用可展示片段并下载原文，浏览器内不承诺精确到段落。
5. Prompt Injection 目前通过 source 边界、XML 转义和系统提示降低风险；更强内容检测留到 P3。
6. 当前仍是默认用户 `default`，没有认证和多租户权限隔离。
7. 同一内容被删除后允许重新上传；更换 Embedding 模型后旧文档因模型名/维度不匹配不会参与检索，需要重新索引。

## 十二、后续如何开发

### 12.1 P2 运行优化

先积累真实个人资料和问题，再按评测结果优化：

1. 增加无答案、相似文档、长文档、表格和中英文混合评测；
2. 记录解析耗时、Embedding 耗时、候选数量和最终 source 数；
3. 增加失败文档重新索引和更换模型后的批量重嵌入；
4. 根据真实 Recall 调整 chunk、top-k、相似度和 RRF 参数；
5. 数据规模明显增大后切 PostgreSQL + pgvector，并用 Alembic 管理迁移；
6. 索引耗时影响交互后再迁移到 Job Queue / Worker。

### 12.2 P3：开始做事

P3 可在当前边界上增加：

- Skill 与 Tool Registry；
- 模型 Tool Calling；
- 权限分级、参数预览和高风险操作审批；
- Tool 执行日志、Run trace 和可观测性；
- OCR、Query Rewrite、Reranker；
- 更强的文档 Prompt Injection 检测。

RAG 继续只提供证据，Tool 才能执行动作；两者不能混为一层。前端仍只渲染后端下发的决策和审批请求。

## 十三、P2 验收结论

P2 已达到修订开发文档的完成边界：四类文件可安全上传和保留原文，可解析、分块、真实 BGE 索引、Vector+BM25+RRF 检索；只有预算内证据进入模型并形成白名单引用；引用可在流式回答和历史消息中持续展示；知识库 UI 可完成上传、查看、检索和删除；固定评测可以重复运行并给出明确基线。

当前实现保持了 P0/P1 的架构和数据兼容性，没有为了未来阶段提前增加重型服务或多层抽象，可以在此基础上进入 P3 开发。
