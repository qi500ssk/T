# Personal AI 项目审查与发布准备报告

审查日期：2026-10-04。审查基线：`e71577d`，GitHub 仓库现地址 `https://github.com/qi500ssk/T`，分支 `main`。本报告随后的提交包含报告本身和一项阅读器 lint 修复。

## 1. 结论

项目已具备本机个人使用的主要功能：对话、角色卡、角色记忆、书籍导入与阅读、TXT/EPUB 导出、原创小说生成、工具审批、MCP 和活动任务。当前服务可正常读取已有书籍，近期角色删除和助手隔离的检查也已通过。

**仍不建议直接作为稳定正式版发布。** 本次复现了恢复任务跳读、角色 ID 碰撞、章节排序/筛选错误和文件夹上传上限不一致。它们可能让“任务显示成功”与“正文读完整、角色正确、章节完整”不一致。应先解决这些数据正确性问题，再发布本机测试版。

**当前架构不能直接作为多人公网服务上线。** README 和部署配置明确面向本机单用户；无登录、统一 default 用户、共享运行时配置和本地文件能力都是这一定位的组成部分。公开 GitHub 源码、本机 Docker 发布和公网 SaaS 上线，是三种不同的交付目标。

本报告区分已经复现、代码确认、需要专项验证和尚未实现的能力。不会把一次构建通过当成所有功能可靠。

## 3. P0：稳定发布前优先解决的数据正确性问题

这里的 P0 表示会破坏项目核心承诺、应阻止稳定版发布；并非声称这些问题已破坏用户现有数据。

### R01：更换模型窗口后恢复阅读，可能直接跳过未读正文【已复现】

位置：`core/story/novel_reading.py:143`，`apps/api/novel_readings.py:128`。

恢复时使用当前 Provider 重新划分 batches，却沿用旧 `completed_batches`。例如小窗口原来有 8 批，已读 3 批；换大窗口后全书只有 1 批，`range(3, 1)` 为空，直接进入角色复核和创建。报告中的 model 也会被新模型覆盖，缺少完整恢复配置证据。

内存探针结果：旧进度 3、新窗口单批时，正文 stream 调用 **0 次**，create_agents 调用 **1 次**。

修复建议：保存源文件 hash、已经完成的字符区间或固定批次清单、任务模型与窗口配置。恢复时验证源文件身份，按已读字符位置继续；配置变化时不得以旧批次序号解释新分段。最后创建前验证所有正文区间连续覆盖。

验收：小窗口暂停后换大窗口、反向切换、源文件修改、批次中断都不能跳字或错误宣称全文已读。

### R02：重复角色 ID 会让不同人物共用角色和记忆【已复现】

位置：`core/story/novel_reading.py:20`、`:74`。

Characters 只校验列表数量，未检查 id 和 name 唯一。两个人都返回 `id=same` 时 schema 接收；角色 ID 使用 job.id 和 person.id 计算，因而两个人得到同一个角色 ID。后一个 profile 覆盖前一个，记忆却会写到同一个角色下。名单比较使用 set，也无法保证人物数量与重复情况一致。

修复建议：生成、复核和落库前均校验唯一 ID、唯一姓名、名单数量和对应关系；ID 不允许在批次之间无说明变化。错误时保留结果并进行小范围修复，不重读全书。

验收：重复 ID、重复姓名、缺失人物、额外人物、同人异 ID 和复核改 ID 必须被拦截，数据库不能产生混合角色。

### R03：章节导入的选择与顺序可能不完整【已复现】

位置：`core/story/books.py:132`、`:154`、`:159`。

- 文件名 `第一章.txt、第二章.txt、第三章.txt` 被排序为 **第一章、第三章、第二章**：natural_key 只识别阿拉伯数字。
- 同一目录包含 `ch001.txt` 和 `第二章.txt` 时，只要发现 ch/chapter 数字文件，就只保留这类文件，第二章会被列入 ignored_files。
- 当前数字排序还不是经过验证的“卷号 + 章号”结构化排序；不能假定所有中文卷名都按剧情顺序排列。

系统会展示被忽略文件，但“未进入正文”不等于该文件确实是说明资料。用户容易在预览中漏看，最终保存一本不完整的小说。

修复建议：统一识别中英文章号、中文数字和卷号；正文候选不能仅因另一套命名存在而排除。无法确定的文件进入待确认列表，提供手动排序和纳入/排除选择。

验收：混合命名、中文卷章、前言/番外、多个子目录以及无章号文件均有明确、可调整的阅读顺序。

## 5. P2：体验、性能及维护优化

### R14：书架列表与每次翻章都会解析整本书【代码确认，规模风险】

`apps/api/documents.py:55` 为全部 Document 调用 read_book；`:69` 翻章再次 read_book。PDF/DOCX 也会在书架请求中解析。列表没有分页，每次响应返回完整目录。RAG 检索还会加载候选全文 chunk 并重新建立 BM25（`core/rag/retrieval.py`）。

当前 6 本左右的小样本书架响应约 0.096 秒，不存在本次已测的严重卡顿；风险在大量长篇、几十万 chunks 后明显增加。

建议：导入时保存书名、简介、目录、章偏移与源 hash；列表分页；读取单章；按内容 hash 缓存；检索建立可失效的词法索引。验收用 100 本长篇和不同 chunk 规模测响应、内存与 DB 查询量。

### R15：预览和确认重复上传、重复解析【代码确认】

`BookImport.tsx:15` 每次 convert(save) 都发送所有 files。确认保存时再次传输和解析整本，浪费内存与时间；当前服务并非真正的流式导入。ZIP 在内存展开，虽然有总量和条目限制，多份并发仍会放大内存占用。

建议：预览返回短期导入 ID，确认只提交书名/排序和 ID；设置并发、超时、临时数据清理。先测现有上限下内存峰值，不必直接引入复杂队列。

### R16：格式支持范围仍有限【代码确认与探针】

- EPUB 按 spine 读取、支持目录顺序，但转成纯文本后没有保留原始 EPUB、封面、插图、脚注和排版。
- XML XHTML 目前以文本提取为主，DRM、图片扫描内容没有实现。
- as_epub 将每一行输出成 p。探针中 `甲乙\n丙丁\n\n第二段` 回读变为 `甲乙\n\n丙丁\n\n第二段`；文字没有少，但段落结构改变。
- 若一个 EPUB spine 文档内存在多个普通 h1 标题，且标题不匹配“第N章/Chapter N”，可能无法拆出正确章节。
- 中文章号中的“序章、楔子、尾声、番外、后记”等也需要规则和人工目录修正。

建议：保存原始文件和规范化文本两份；结构化记录段落与章节。自动换行用于展示时应避免破坏诗歌和明确保留换行的内容，提供原文排版选项。

### R17：重复正文导入不采用新书名【代码确认】

`save_source` 按正文 hash 去重，命中旧 Document 后直接返回旧 id。用户在预览中改书名再导入同正文，结果可能仍是旧书名。

建议：明确展示“已存在”；允许修改书名或创建新版本。保留内容去重，但不要让用户输入无声失效。

### R18：删除与历史任务之间的语义尚未统一【代码确认】

删除角色保留了 NovelReading.result/report。以后对旧 completed 任务调用 `/check`，create_agents 可能按确定 ID 重新生成已删除角色。Document 删除会移除数据库与上传原文，但不清理 `worldbooks/novel-id/original.txt` 等副本；用户对“删除书籍”的磁盘行为可能有不同预期。

建议：角色有删除标记/任务状态能识别人工删除，重建必须明确操作；书籍删除说明是否仅从书架移除还是连磁盘副本删除。书籍和角色生命周期分开，但需要可解释的对应关系。

### R19：模型选择与主对话不完全一致【代码确认】

ChatRequest 可以选择 model_profile_id，阅读/写作任务却从全局 settings 创建 Provider，不能跟随当前对话的模型选择。任务恢复再次用当前全局配置，与 R01 组合风险较大。模型切换保护主要检查 AgentRun，不能据此认定独立资料任务也被冻结。

建议：任务明确记录/展示使用的模型，并固定其配置快照或指定 profile；恢复时解释变化，不覆盖原审计信息。

### R20：错误和进度需要更直接的用户表达【代码确认】

部分前端 catch 使用 String(e)，用户会看到技术异常或“请求失败 409”。阅读进度、输入 token 有显示，但上下文估算与供应商计费并不完全等价；usage 缺失会按 0 统计，可能让人误以为无消耗。章节内滚动位置未保存，只有章节号；设置 localStorage 写入也缺少统一失败处理。

建议：区分“服务未返回用量”和“实际为零”，展示阶段与可恢复原因；保存章节内位置；集中处理 API 错误。用户要求的一次确认删除继续保留，不增加多层确认。

## 6. 功能入口、旧代码与文档一致性

### R21：下载小说流程仍留在后端【代码确认】

用户当前定位是只导入下载好的小说。前端独立搜索入口已移除，助手 workflow 也声明不负责下载；但 `apps/api/novel_readings.py` 的 ReadBody 仍接受 search_query/url，`core/story/novel_source.py` 仍会搜索并下载全文。这不是无法到达的死代码：API 仍可调用。

建议：按当前产品要求决定删除联网小说来源分支、保留通用助手联网搜索。不要把后端接口残留当成已经实现了可靠的章节站抓取；现有获取逻辑也不支持一般分章节网站的完整遍历。

若继续保留直连 fetch，DNS 预检查与 httpx 实际连接仍是两次解析，尚未证明防住 DNS rebinding；本轮未做恶意网络探测。公网使用前需要绑定验证后的连接目标或受控代理。

### R22：助手还不能自动完成完整“读书→创建角色”编排【代码确认】

书籍详情里的 NovelReader 能发起任务；技能/执行工具注册中未找到调用 novel-readings 的能力。StoryOpening 的导入意图跳转书架，续写意图传 document_ids 做检索。这些入口能引导用户，但不等于聊天助手已具备自动读取全书、启动同一任务、持续汇报、创建角色的完整工具链。

建议：让助手调用同一受控后端能力、使用同一任务记录，并保持“本次选中的书”。可以先做好页面入口，再补自动编排，不能只通过提示词承诺已经有工具。

## 7. 如果要上线，会遇到什么问题

### 7.1 发布本机个人版 / Docker 版本

现有端口只绑定 127.0.0.1，符合当前本机定位。应完成 R01–R04 等核心正确性问题，并做以下验收：

1. 从全新 clone、无运行时配置、空数据库执行 compose up，确认无模型时有清楚引导、导入/阅读仍可用。
2. 从上一发布版保留卷升级；现有 config/plugins/skills 卷可能继续保留旧内容，需要明确同步策略，不能认为 rebuild 自动覆盖所有用户卷。
3. 本机指定目录和容器 /workspace 的差异必须在页面解释；数据落在容器挂载卷或绑定路径，不能保证每个用户都有 E 盘。
4. 执行备份、恢复、容器重启中断、继续任务、取消任务、断网/429/输出截断和文件损坏验收。
5. 固定 MCP 与镜像版本，验证浏览器是否可用；后端容器当前以 root 运行，考虑切换普通用户并限制必要写目录，但需先验证卷权限。
6. health 当前只证明 DB 能 SELECT 1，不能证明模型可用、MCP 连通或任务系统健康；提供分项状态，模型未配置不必导致书架不健康。

### 7.2 部署公网地址供自己远程使用

当前不能只把 127.0.0.1 改成 0.0.0.0。至少要有认证、TLS、访问限制、上传体积与速率限制、密钥保护和反向代理 SSE 配置。`X-Requested-With: PersonalAI` 是可伪造的请求标记；CORS 和这个标记不是身份认证。

GET 接口目前可读取会话、记忆、资料等单用户内容，写接口也可以被知晓标记的客户端调用；公开暴露相当于暴露整套本机个人软件。还要检查工具、MCP、模型设置、文件操作等管理接口的访问权限。

### 7.3 面向其他人提供多人网站 / SaaS

以下核心能力尚未实现，属于另一个明确扩大的产品范围：

- 用户身份、登录会话、账号注销与每个资源的归属授权。
- 跨用户角色/记忆/书籍/任务/向量/文件隔离；运行时模型密钥不能用单份全局 JSON 共享。
- 用户配额、模型费用上限、限流、存储配额、任务并发和滥用控制。
- 多实例任务队列、幂等执行、共享审批/任务状态和故障恢复。
- HTTPS 部署规范、管理后台隔离、监控告警、备份恢复和数据删除策略。
- 用户资料及上传小说的隐私、保留与使用规则。商业发布涉及哪些法律义务需另行确定，本报告没有做法律合规审查。

不要为当前个人版提前补齐所有 SaaS 系统；先确定是否真的改变项目定位。
